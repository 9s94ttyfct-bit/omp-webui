# v0.17.0 design: a new project for each new chat, a quieter "writing" animation, Windows self-update, remembered guidance

Date: 2026-11-01. Approved by the person in conversation (parts 1–3); part 4 was asked for at approval, and its
details are my calls, open to change. Base: `main` at v0.16.0 (`8ab2744`). The four parts are independent; each gets its
own issue and commit(s), and they ship together as v0.17.0.

## 1. New chat starts a new project by default

**Why.** The person wants every new conversation to live in a project folder of its own under one root they choose,
without hunting for "New project folder" inside the folder picker. Today New chat silently reuses the most recent
project (`NewChat.tsx`: `cwd` from `PREF.cwd`, else `recent[0]`), and "New project folder" (`NewProjectFolder.tsx`,
`server/projects.ts` `ProjectsFolder`, root in Settings › Projects folder, default `~/omp`) is one level down in the
picker.

**Decided (by the person).**
- New chat defaults to a **new project**. Using an existing folder is something the person picks.
- The root stays settable (it already is: Settings › Projects folder); New chat shows the root and lets the person change
  it from there.

**Proposed (mine, agreed in conversation):**
- The folder row of New chat becomes a "New project" field, focused, with the root shown under it ("Made in ~/omp ·
  Change") and a "Use an existing folder" button that opens today's `DirBrowser`.
- The name may be left empty: the folder is then named `chat-YYYY-MM-DD-HHMM` (local time); a name that exists gets
  `-2`, `-3`, … The typed name is checked as today (`projectNameProblem`, again on the server).
- **The folder is made when the first message is sent**, not when New chat opens or a name is typed: cancelling leaves
  nothing behind. Then omp starts in it and the message is sent.
- **Cost the person accepted:** with a new project there is no folder to warm omp up in, so the first reply comes a few
  seconds later than today. Picking an existing folder keeps today's warm-up.

**Goals.**
- Default every time New chat opens: new project, empty name. The choice is not remembered across New chats.
- Entry points that already know their folder keep it and skip the new-project default: today that is "Start a chat
  about this issue" (`IssuesTab.tsx` `toNew`, which sets `PREF.cwd`). They open New chat in "existing folder" mode on
  that folder.
- A remote page can make a project in the root (as today) but not change the root (as today: `remoteNote`).
- Errors the server gives (root gone, not a folder, no permission, name exists between check and send) are shown at the
  field, and the draft stays; nothing is sent.
- Everything New chat sets before the first message (model, permission mode, guard, guidance, unattended, goal mode,
  preset) still applies to the conversation started in the new folder.

**Non-goals.** No change to how projects are listed or grouped in the sidebar; no deleting of empty project folders;
no git init or template in the new folder.

**My calls (after the builder check; the person can overrule).**
- **Pickers before the folder exists.** The model, preset, thinking and permission pickers, `/commands` and the usage
  meter come from the warm-up omp process. In new-project mode that process is warmed up in the root, only to drive
  them; on send, a process is started in the new folder and the picks are carried over with the mechanism New chat
  already has for a process started after a folder change (`picks` in `NewChat.tsx`). Nothing the person sees changes.
- **Invariant: the root process never receives the person's input.** Today every send path of New chat (a prompt, a
  `!command`, a goal, a guided goal) goes to the warm-up process (`warmId`). In new-project mode each of them must go to
  the process started in the new folder; the root process only takes the pickers' settings (model, thinking, preset,
  permission mode), never a prompt, a command or a goal, and it is closed when the new one runs. A test sends a
  `!command` that writes a file and checks it lands in the new folder, not in the root.
- **No trace of the root process.** It is opened and closed the way a warm-up process is today when the folder changes
  (`closeLive` on an unsent process). The implementation checks that this leaves no conversation, no session file and no
  "recent project" entry for the root; if omp does write one, the design is revisited before going on.
- **"Change" for the root** in New chat changes the same setting as Settings › Projects folder (global), not this chat
  alone.
- **`PREF.cwd`** no longer picks New chat's folder. An entry point with a folder (the issue's "Start a chat") passes it
  in the view (`{ kind: "new", cwd }`), which opens New chat in existing-folder mode; the scripts and tests that set
  `ompw.cwd` (`scripts/soak.ts`, e2e specs) are moved to that. On a remote page the issue flow keeps its folder as
  today.

**Left to the builder.** How the start after "send" is sequenced (make folder → start live → send), and how the
draft/attachments survive a failed folder creation; the phone layout of the "New project" field and "Change" (same
controls, laid out to fit).

## 2. Live animations: replace the shimmer band; find the stutter

**Why.** The person finds the shimmer band ugly, and sees animations stutter at times.

**What it is today.** `.live-shimmer` (`index.css`) is an absolutely positioned layer the size of the whole reply being
written (`Message.tsx`) and of the turn's running figures (`TurnStats.tsx`); its `::after` is an accent gradient swept
across with `transform`. The earlier measurement (`docs/TECHNICAL.md`, Live animations) used one short fake-omp turn and
found no added paints.

**Stutter: a hypothesis, not a finding.** The band's layer is as tall as the reply; as the reply grows, the layer may be
re-rasterised at every new size, more so for long replies. This is unverified. **First step:** record a Chrome
performance trace of a long streamed reply (thousands of lines, Normal and Lively), with the agent graph's particles and
the completion burst, animations on and off; find which frames drop and why. Fix what the trace shows, whatever it is;
removing the band is not assumed to cure it.

**Decided (by the person): option A.**
- Remove the shimmer band from the reply and from the turn figures.
- At the end of the text being written: a small caret that breathes (opacity), like ChatGPT's or Claude's, while that
  reply streams; gone when it stops.
- The running time in the turn figures: a soft glow on the digits only (text, not a box).
- Intensity (Subtle / Normal / Lively) still scales them; reduced motion turns them off; the Settings switch is
  unchanged.

**Goals.** Idle still costs nothing (`tests/e2e/live-motion.spec.ts` keeps holding: no running animations and 0
animation frames after the turn). A trace of the long reply after the change shows no dropped frames attributable to the
animations, compared with animations off; the numbers go into `docs/TECHNICAL.md` in place of the old table.

**Left to the builder.** The caret's exact look per theme; where the caret sits when the reply ends in a code block or
a table.

## 3. Windows: the launcher updates itself

**Why.** The person wants Windows users to get updates without downloading the zip by hand. Decided (by the person):
the folder-swap approach below, not an installer.

**What exists.** The app updater (`server/update/`) is macOS-only: it looks for `omp-webui-v<version>.dmg`
(`release.ts` `installerName`), verifies a signed `.app`, and hands over to `helper.sh`, which swaps app bundles and
relaunches with `open`. The capability `appUpdate` is off on Windows. Reusable: the release check (GitHub API, ETag,
every 6 h), the page's Updates card and notice, the "wait for conversations" confirmation, outcome reporting.

**Design.**
- On Windows the release's asset is `omp-webui-v<version>-windows-x64.zip`. The updater takes the asset's `digest`
  (`sha256:…`) from the GitHub release answer; an asset without one is not installed.
- Install: download to `<data dir>/update/`, check size and SHA-256, extract to `<install folder>.updating` beside the
  folder the running `omp-webui.exe` is in, check that it holds `omp-webui.exe` and `web/index.html` and that
  `omp-webui.exe --version` prints the expected version.
- Hand-over: write a PowerShell helper (like `helper.sh`) that waits for this process to exit, renames the install
  folder to `.previous`, the staged one into its place, starts the new `omp-webui.exe`, and records the outcome; if any
  step fails it puts the old folder back and starts it. The server then exits (closing its console window). The new
  launcher opens the page as on any start; the page shows the outcome as on macOS.
- Refused, with the reason on the Updates card: not started from the launcher (a source checkout), install folder not
  writable (e.g. under Program Files), not enough space.
- The data folder is outside the install folder and untouched.

**Security, said plainly.** The program is unsigned. The SHA-256 comes from GitHub with the zip, so it guards against a
broken or altered download, not against a compromised release or account; that is the same trust as downloading the
zip by hand. Whether SmartScreen or antivirus warns about the replaced program is not known (a download made by the
updater carries no "downloaded from the internet" mark, but SmartScreen also judges unsigned programs by reputation);
it needs the check on a real Windows PC, and the docs do not promise either way.

**Tests.** The swap, the rollback and the relaunch run in CI on `windows-latest` against the built launcher and a fake
release server (`OMP_WEBUI_APP_UPDATE_API`), including a failure mid-swap. A real Windows PC is still needed for a
final hand check (console window, antivirus); none is available here, so the release says this was tested on CI
runners only.

**Non-goals.** No installer, Start menu entry, uninstaller, ARM64 build or code signing.

**Getting there from 0.16.0.** The 0.16.0 launcher has no updater for Windows: its users update to 0.17.0 by hand once
(download the zip, replace the folder), as `_install.md` says; from 0.17.0 on it updates itself.

**Left to the builder.** How `appUpdate` becomes per-platform (capability text, the page's copy for Windows), the
helper's exact form, and how the install folder is found from `process.execPath`.

**My calls (after the builder check; the person can overrule).**
- **Zip layout.** The zip stays as CI makes it (one top folder, `omp-webui-windows-x64/`); the updater unwraps that one
  folder and requires `omp-webui.exe` and `web/index.html` in it.
- **Version check.** The launcher gets a `--version` mode in 0.17.0 (prints the version and exits; no server, no
  browser). The updater runs the staged exe with it and refuses a mismatch. The SHA-256 says the bytes are the release's
  asset; `--version` says that asset is the version the release announced. 0.16.0 has neither (it updates by hand), so
  no fallback is needed.
- **Leftovers.** `.previous` is kept until the new version has started and served its page once, then removed; a stale
  `.updating` or `.previous` from an earlier attempt is removed before the next one starts (as the macOS updater does with
  its staged copies).
- **Windows.** The helper runs hidden; the new `omp-webui.exe` is started in a console of its own, as a double-click
  would, and opens the page.

## 4. New chat remembers the guidance last used

**Why.** The person wants New chat to start with the model guidance the last new chat was started with.

**What exists.** New chat starts from the template Settings makes the default for new chats (`ompw.guidanceDefault`,
`startGuidance` in `NewChat.tsx`); a pick in New chat (`guidancePick`) applies to that conversation only.

**My calls (the person can overrule).**
- When a conversation is started from New chat (its first message is sent), the guidance it was started with is
  remembered as a synced preference (follows the person to every browser and port, like the others): a template by its
  id, text written in New chat as that text, or "none". A pick that is never sent is not remembered.
- New chat starts from the remembered guidance. With nothing remembered yet, or a remembered template that was deleted
  since, it starts from Settings' default as today. Settings' help text says so ("used until a new chat is started with
  another").
- Text written in New chat is remembered up to the length the guidance editor allows; a template edited since is used
  as it is now (by id), as today.

**Goals.** Start a chat with template B, open New chat again: B is picked. Start one with "none": the next starts with
none. Delete B: the next New chat starts from Settings' default.
