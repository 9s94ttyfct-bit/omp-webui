# v0.19.0 design: filters for Plugins and Skills, skills switched on and off, deeper usage analysis, Windows on Arm

Date: 2026-11-04. Asked for by the person in four points; approved in conversation ("2 supports both global and per
project folder; the rest as you proposed"). Base: `main` at v0.18.9 (`15cb873`). The four parts are independent and ship
together as v0.19.0. What is marked *(my call)* was not discussed and may be changed.

## 1. Advanced filters on the Plugins page, by marketplace among others

**Why.** The Discover list (every plugin of every added marketplace) and the Skills list grow long, and the only way to
narrow them is one text field. The person wants to see one marketplace's plugins, and to filter further.

**Today.** `server/omp/plugins.ts` parses the *text* of `omp plugin discover <marketplace>`: each item has name, version,
description, marketplace and where it is installed. The marketplace's cached catalog
(`~/.omp/plugins/cache/marketplaces/<name>/marketplace.json`) also has `category`, `author`, `homepage`, `tags`,
`keywords` and `skills[]`, which the page never sees.

**Decided.**
- Discover: filter by **marketplace** (one or all), **category**, **installed or not**, plus the text field (which now also
  matches author, tags and keywords); **sort** by name, marketplace or category. The filters show only the values the
  list has, with counts.
- Installed plugins: filter by marketplace (and source), enabled or not.
- Skills (installed): filter by **provider** (plugin, user folder, registry, Claude's folder…), **level** (user, project)
  and **on/off**; the registry search sorts by downloads or name and can hide deprecated skills.
- *(my call)* The catalog details come from the cached `marketplace.json` that omp itself writes, read by the server next
  to omp's answer and matched by plugin name; a catalog that cannot be read leaves an item with the details omp gave, and
  nothing fails. The chosen filters are not remembered across visits (the text field is not either).

## 2. Skills managed, and switched on and off one by one

**Why.** Many skills are discovered (plugins, `~/.omp/agent/skills`, `~/.claude/skills`, the registry); the person wants to
turn single skills off and on, for every conversation or for one project folder.

**Today.** omp turns a skill off with `skill:<name>` in its `disabledExtensions` setting. The Loaded dialog of a
conversation writes the global list (`server/omp/toggles.ts`); a folder's `.omp/config.yml` may set its own list, which
*replaces* the global one there. The Plugins page's Skills tab shows no on/off state.

**Decided (by the person).** Both scopes: **global** (all conversations) and **per project folder**. Not per conversation.

**Proposed (my calls).**
- The Plugins page's folder picker already chooses home (user scope) or a project folder. On the Skills tab each skill gets a
  switch: with home chosen it writes the global list (`omp config set disabledExtensions`, as the Loaded dialog does);
  with a project folder chosen it writes that folder's `.omp/config.yml`.
- A project's list replaces the global one, so the first project change copies the global list into the folder and edits
  it; the row says when a skill is off because of the global list or because of the folder's, and a folder whose list
  exists offers **Follow the global list** (removes the folder's `disabledExtensions`).
- The project file is edited in place: only the `disabledExtensions` entry is rewritten (comments and every other key are
  kept), the file is written whole and moved into place, and a file that is not readable YAML is not touched (the row says
  why).
- Bulk: select several skills and turn them on or off together; a filter by on/off (part 1).
- Each skill row shows where it comes from (path), and opens its `SKILL.md` read-only; a registry skill can be uninstalled
  (`omp skill uninstall`, `-g` at user level).
- Running omps watch their config and rediscover skills; nothing is restarted.

## 3. More model and cost analysis on Usage & cost

**Why.** The page answers "how much in total and by model/project/agent", but not "which conversations, tools and errors
cost the most in this period" or "which model is cheapest for what it does".

**Today.** `server/omp/stats-db.ts` reads omp's `stats.db` by hour, model, provider, folder and agent type. Unused:
`messages.session_file`, `error_message`, `service_tier`, the `tool_calls` table. "Most expensive conversations" is
all-time and built in the page.

**Decided (my calls).**
- **Conversations in the range**: cost, requests, tokens and models of each conversation (by `session_file`) in the chosen
  range, top 20, each opening its conversation; replaces the all-time list.
- **Model comparison**: per model, cost per request, cost per million tokens, cache hit, output tok/s, time to first
  token, error share; sortable.
- **Tools**: per tool, calls, errors and error share, average result size, for the range.
- **Errors**: the most frequent error messages by model, with counts and last seen.
- **Time of day**: requests and cost by hour of the day (local time), a small heat strip.
- The new figures come from the same read-only queries of `stats.db`; a database without a column the new parts need hides
  that part and keeps the rest.

## 4. Windows on Arm (arm64)

**Why.** The person wants the Windows build on Arm machines too. (The v0.17.0 design listed an Arm64 build as a non-goal;
this lifts it.)

**Decided (my calls).**
- A second launcher zip, `omp-webui-vX.Y.Z-windows-arm64.zip` (top folder `omp-webui-windows-arm64/`), built with Bun's
  `bun-windows-arm64` target on GitHub's `windows-11-arm` runner (native, so the icon and version resources are kept),
  next to the x64 one in CI and in the release.
- The updater picks the zip of the machine's processor (`installerPlatformOf` takes the arch); an x64 launcher keeps
  taking the x64 zip.
- No built-in browser engine exists for Windows on Arm (Chrome for Testing has no build): the Browser settings say so, as
  for any system without one. cloudflared runs as the amd64 build (Windows emulates it), as today.
- Docs (README, `docs/agents/updates.md`, TECHNICAL) name both zips.

## Non-goals

- Skills switched per conversation.
- Popularity figures for plugins (catalogs have none).
- A Windows Arm build of the macOS app's parts (none exist on Windows).
