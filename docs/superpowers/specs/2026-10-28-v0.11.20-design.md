# v0.11.20 design: session panel, usage history, guidance editing, sidebar content search, Apple model benchmark

Date: 2026-10-28. Approved by the person in conversation. Branch `next-0.11.20` (worktree `../omp-webui-next`, on
v0.11.19 = `48c3d899`, already carries #707 and #708). The parts are independent; each gets its own issue and commit(s).

## 1. "This session" panel: common settings on top, the rest folded

**Why.** The slider popover (`web/src/components/SessionControls.tsx`) lists nine settings in one column, each with an
"About" disclosure, then the conversation's guard (`SessionGuard`), Full/Light (`SessionMode`) and Compact now. It needs a
long scroll; the person wants it tidy and short.

**Decided (by the person): common settings visible, the rest under a collapsed Advanced section.**
- Visible: Auto-compaction (with its Compact at row), Fast mode (and Slow mode when it applies), the guard section,
  Full/Light, Compact now.
- Under Advanced (collapsed by default): Auto-retry, Steering delivery, Follow-up delivery, Interrupt, Cache warming.
- "About" becomes a small info icon per row that opens the same text, instead of a disclosure line under every row.

**Goals.** No scrolling at 1280×800 with Advanced closed. Nothing removed: every setting and its help text stays reachable.
Advanced shows a dot when any setting inside it is not at its default. A settings-search result that targets a folded row
opens Advanced.

**Non-goals.** No change to what a setting does or how it is sent. No new settings.

**Left to the builder.** Whether Advanced's open state is remembered; exact icon and spacing.

## 2. Usage & cost shows the whole history, 30 days by default

**Why (verified).** `server/omp/stats.ts:30` runs `omp stats --json`. On omp 18.13.3 that returns a rolling ~24 h window
(run 2026-10-28: 10-27 22:28 → 10-28 22:27, 708 requests) and has no range flag (`omp stats --help`: `--port --host --json
--summary`). `~/.omp/stats.db` holds everything since 2026-09-18 (116,535 requests, $5,984). Why the person notices it
after an update is not proven; the likeliest reading is that the page shows a fresh 24 h slice after the restart.

**Decided: approach A, the server reads `~/.omp/stats.db` read-only for the chosen range.**
- Range control on the page: 24 h, 7 days, 30 days, All time. Default **30 days**; the choice is remembered (pref).
- `omp stats --json` still runs as now: it is what syncs new transcripts into `stats.db`. The range answer is computed from
  the database after that sync (or as it is while a sync runs; the page already says "refreshing").
- The answer keeps the shape the page reads (`OmpStats`, `web/src/lib/api.ts`: `overall`, `byModel`, `byFolder`,
  `byAgentType`, `timeSeries`, `costSeries`, `modelSeries`, `modelPerformanceSeries`). Series are hourly for 24 h, daily
  beyond. `UsagePage` / `usage-series.ts` change only for the range control and bucket size.
- Source: table `messages` (timestamp, model, provider, folder, agent_type, tokens, costs, duration, ttft, stop_reason).
- **One window for everything.** The range's start and end (`from`, `to`) are decided once per request and used by both the
  database queries and the guard bucket (`server/guard-usage.ts`, `withGuardBucket`, which today takes its window from
  `overall.firstTimestamp/lastTimestamp` of the answer). The guard bucket must never count requests outside the range the
  rest of the page shows. Its transcript reading must stay fast over 30 days and All time (measure; cache per transcript by
  size and mtime if not).
- Opened with `bun:sqlite` `readonly: true`; never written.
- **Contract test** (`tests/contract/`) against the installed omp: the columns used exist, and the 24 h figures equal
  `omp stats --json` for the same window.
- Fallback: when `stats.db` cannot be opened or lacks the columns, the page shows the `omp stats --json` answer as now,
  labelled "last 24 hours" with the reason.

**Left to the builder.** Query parameter vs route (`/api/stats?range=30d` recommended); caching per range.

## 3–4. Model guidance: edit in place, also when the conversation is not running

**Why.** The Guidance tab (`RightPanel.tsx:219-232`, `GuidanceRow.tsx`) shows a one-line summary and a Change button that
opens a dialog (`GuidanceDialog`, `GuidanceChoice.tsx`); picking a template or saving text applies at once and closes it.
Editing text means "Write your own…", which detaches it from its template. A conversation with no process shows only "no
process": the server reads its kept choice (`/api/model-guidance/session?file=`) but cannot change it. Templates
themselves are edited in Settings › Model guidance, which works and is not changed.

**Decided.**
- The tab body is the editor, no dialog: a template menu (None / templates / Custom) and a text box with the text the
  conversation carries now, editable directly. Save and Revert appear when the text differs.
- Saving text that came from a template asks: **This conversation only** (carried as custom text; template untouched) or
  **Also update template "X"** (the template is saved with the new text through the existing store; every conversation
  using it gets it at its next turn, as template edits already do). Custom text saves without a question.
- A conversation that is not running gets the same editor. Its change is written to the kept record
  (`model-guidance-sessions.json`, `GuidanceSessions`) and carried when it is next opened; the tab says so in one line.
  Server: the change route accepts a session `file` as well as a `liveId`, on this computer only, as the live change is.
  To verify while building: a resumed conversation actually carries the edited record (resume path in `live.ts` reads
  `keptGuidanceOf`), and a conversation opened meanwhile by another page does not lose the edit.
- New chat's picker (`GuidancePicker`) keeps working; it may reuse the editor.

**Non-goals.** No change to the extension or to how the text reaches omp.

## 5. Sidebar search finds conversations by what was said in them

**Why.** The sidebar filter (`web/src/lib/session-search.ts`) matches titles and project names only. Only ⌘K searches
message text (`/api/search`, FTS5 trigram over user and assistant text blocks, `server/search-index-worker.ts`).

**Decided (by the person): titles first, then content matches; scope is what the person and the agent said** (the index
as it is; tool calls, tool output, thinking and subagent transcripts stay out).
- Title matches show at once (local); content matches follow, debounced, each with one line of matching text.
- Within the sidebar's own filters (project, date range, archived view): a match outside them is not shown.
- A conversation matched both ways shows once, as a title match.
- Clicking a content match opens the conversation at the matching message, as ⌘K's message hits do.
- No silent cap at ~17 conversations: the sidebar asks for enough conversations, newest first among equal matches, and
  says when there are more.
- Multi-word queries match all words in any order in the sidebar. ⌘K is unchanged unless it falls out for free.

**Left to the builder.** Debounce; minimum query length for content; how "more" is shown.

## 6. Apple Foundation Models as guard reviewer: benchmark only

**Found.** On this Mac (macOS 27.2, M4 Pro) `SystemLanguageModel.default` is available, context 8192 tokens, 0.5–2 s per
answer. In a four-sample probe the model answered ALLOW for `ls -la src` and BLOCK for `rm -rf ~/Library/Application\
Support/Anki2`, `git push --force origin main`, `xargs -I{} rm -rf {} <<< ~`. Four samples on one machine; not a
measurement, and not evidence for other Macs.

**Decided: benchmark first, no product change.** The guard benchmark (`server/guard-bench.ts`) takes a `ReviewerSource`
(`server/guard-reviewer.ts`). Add one that asks the on-device model through a small Swift command-line helper (stdin:
system + user prompt; stdout: answer), run the shipped cases with the real prompt (`reviewPrompt`,
`server/omp/gate/review.ts`), and compare with the current reviewer on the same cases.

**Report.** Per case: correct allow / correct deny / wrong allow / wrong deny; latency; refusals by Apple's guardrails;
answers that were not the required JSON (try guided generation if plain text fails); prompts over 8192 tokens. A
recommendation: replace, first pass + escalate, fallback only, or not usable. The helper is deleted if not usable.

## 7. Agent graph page (#719)

**Why.** A conversation's subagents are a list in the right panel's Agents tab; who started whom, which ran as one
`task` batch, and who wrote to whom are not visible. Requested: a page like omp-console's agent graph (MIT, read for
reference only, no code copied).

**Decided (by the person).** In v0.11.20. The page lists the running conversations at the left and draws the chosen
one's graph at the right. Edges: who started whom, and messages between agents. A click on a subagent opens its live
view (the Agents tab's `AgentDetail`) beside the graph; a click on the main agent opens the conversation.

**Design.**
- Route `#/agents` (`#/agents/<file>` for a chosen conversation), item "Agent graph" in the sidebar/rail pages
  (`lib/nav-layout.ts`), `View { kind: "agents"; file?: string }`. The page listens to the chosen conversation's process
  as the chat view does to the one on screen (`viewedLiveId`): a process off screen is not listened to (#592).
- Graph model `lib/agent-graph.ts`, pure: nodes = main agent + `useAgentRows` rows (live frames and transcripts on disk);
  column = nesting depth (`Parent.Child`), rows by a tidy-tree pass; siblings started by one `task` call
  (`parentToolCallId`) framed as a batch; stalled = running and no frame for 2 min (`updatedAt`); totals: running,
  total, stalled, tokens, cost (`rowSpend`).
- Message edges: `write` tool calls whose `path` is `agent://<id>` (`agent://all`: to every other subagent), from the
  main agent's and each subagent's tool calls the page holds (live `tools`; a subagent keeps its last 20 finished). Count
  per sender→recipient pair. Not from transcripts on disk: an edge is what was seen live.
- Drawing: hand SVG for edges, HTML buttons for nodes (keyboard and screen reader), zoom in/out/fit; legend.
- Not in scope: advisors (no live frames), dragging nodes, collapsing subtrees.
