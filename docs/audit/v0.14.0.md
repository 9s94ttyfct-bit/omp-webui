# omp-webui v0.14.0 audit

Baseline: `main` at v0.13.0 (commit `48a90d2`). Branch: `audit/v0.14.0`. Report only: no code was changed.

omp reference: the latest release, **18.14.1** (the installed Homebrew build reports `omp/18.14.1`), read against the
release notes of 18.11.0 through 18.14.1 and against upstream `docs/rpc.md`,
`packages/coding-agent/src/modes/rpc/wire/commands.ts`, `wire/events.ts` and `src/tools/approval.ts` at the tags
`v18.11.0` and `v18.14.1`.

## 1. Summary

- **30 findings**: 0 high, 12 medium, 18 low (§4). Each has a fix plan, a regression test and an effort; all were `open` when the audit was written (the Status column says what was fixed since, in which commit, with which test).
- **omp compatibility.** Every RPC command the server and the page send exists in omp 18.11.0 (extracted with
  `tests/support/omp-interfaces.ts`' `scanRpc` and compared with the 18.11.0 command table), and the wire changes
  18.11.0 → 18.14.1 are additive (new commands `live_connect`, `dictation_start/stop`, `get_session_lease`, `navigate_tree`,
  `abort_branch_summary`, `set_label`; new events `manual_compaction_start/end`; `AgentStartEvent.resumedToolCallIds`).
  Nothing the app uses was removed or renamed. The gaps are: a declared minimum below what the app needs (A-001), CI that
  only ever tests the newest omp (A-002), new events and frame fields the app ignores (A-003, A-005, A-006), and one
  private omp mechanism re-implemented now that omp has a public interface for it (A-004).
- **Most important outside compatibility**: the risk classifier that both the default-on Guard and the remote
  confirmation rely on lets several command shapes through unseen (A-007); a `config.yml` that another omp moved aside is
  never reported (A-008, also the cause of flaky issue #15); presets go stale in running conversations (A-009, issue #4).
- **Known small items**, all confirmed and given a root cause: Markdown editor error screen and Escape (A-010, root cause
  found with a probe), unlabelled chat task-list checkboxes (A-011, confirmed in the browser), `#heading` links (A-012),
  diff line-number contrast (A-013, measured per palette), Settings-help e2e (A-026: 64/64 passes, one latent race),
  CI notifications in the macOS app (A-015: treated as a finding, with a fix through the existing shell bridge).
- **Open issues #1–#15**: all still valid except #3 (partly mitigated) and #9 (first-load part now within budget); each
  is a finding below with its current root cause and fix plan (table in §5).

## 2. Minimum supported omp version

**Decision: raise `OMP_COMPAT.min` from 18.11.0 to 18.12.3** (range `>=18.12.3 <19.0.0`).

Rationale:

- Today the app enforces `>=18.11.0 <19.0.0` (`shared/omp-install.ts:16`): an older omp gets a warning on every page,
  an update to a release outside the range needs confirmation. The RPC surface the app uses is fully present in 18.11.0.
- But the app offers the approval mode **Ask and remember** (`always-ask-cached`, `shared/approval.ts:6`,
  `web/src/components/ApprovalPicker.tsx:25`) unconditionally, and writes it as `tools.approvalMode` into the process's
  `--config` overlay. omp added that mode in **18.12.3** ("Added the Ask and remember approval mode
  (`tools.approvalMode: always-ask-cached`)", 18.12.3 notes). On 18.11.0–18.12.2 the value is unknown to omp. What
  omp then does (falls back to its default, or rejects the overlay) was not executed here [inference]; either way the
  conversation does not run in the mode the page shows, which for a safety setting is wrong.
- Other features were measured on later versions (profiles under `~/.omp/profiles` on 18.12.4, `server/sessions/roots.ts:77`;
  model guidance on 18.12.6, `server/omp/guidance/extension.ts:14`; the stats database on 18.13.3,
  `server/omp/stats-db.ts:8,46`), but each degrades without breaking (a wrong guess is caught, e.g. `holdsLatest` for
  stats). They do not force a higher floor; they are covered by the matrix below.
- Adopting `omp session lease` (A-004) or `manual_compaction_*` (A-003) does **not** need a higher floor: both have a
  documented fallback for older servers.

### Recommended CI omp matrix

| Entry | omp | Runs | Why |
| --- | --- | --- | --- |
| `min` | `18.12.3` (= `OMP_COMPAT.min`) | unit + contract shards | the floor the app declares is the floor it is tested on |
| `latest` | `latest` (npm dist-tag) | unit + contract + e2e (as today) | what users update to |
| scheduled | `latest` | unit + contract, daily `schedule:` | the comment in `shared/omp-install.ts:11` already promises "every day"; today nothing runs without a push |

How to install a pinned omp in CI (npm has every 18.x release; `@oh-my-pi/pi-coding-agent` needs `bun >=1.3.14`):

```yaml
strategy:
  fail-fast: false
  matrix:
    os: [ubuntu-latest]
    omp: ["18.12.3", "latest"]   # keep the first equal to OMP_COMPAT.min (a unit test checks it, see A-002)
    shard: [1, 2, 3]
steps:
  - name: Install omp ${{ matrix.omp }}
    run: |
      bun install -g "@oh-my-pi/pi-coding-agent@${{ matrix.omp }}"
      echo "$HOME/.bun/bin" >> "$GITHUB_PATH"
  - run: omp --version   # fails the job early if the pin did not install
```

The e2e job stays on `latest` only (16 shards × 2 is not worth it: e2e uses a scripted omp for nearly every spec).

## 3. What was checked, and how

- **omp interfaces**: every row of `docs/TECHNICAL.md` › "How it stays compatible with omp updates" against the 18.11.0
  → 18.14.1 notes (breaking changes, removals, renames, RPC, extension API, config keys, CLI flags); the RPC command
  table and event table diffed between the two tags; the extension API events the app's own extensions use
  (`before_agent_start`, `context`, `tool_call`, `before_provider_request`, `cache_warming_decision`) checked for changes.
- **Long-running behaviour** (code review): every `setInterval` in `server/` and `web/src/`, every long-lived `Map`/`Set`
  of `server/live.ts`, `server/main.ts`, `server/push/hub.ts`, `server/shell-events.ts`, `server/omp/relay*.ts` and
  `server/omp/rpc-client.ts` (entries removed on exit, or bounded), the WebSocket outbox (bounded by `MAX_QUEUED`, slow
  pages closed), the page's reconnect (capped exponential backoff), the relay's backlog bound. No leak or unbounded
  structure was found there; nothing was soak-tested.
- **Probes run** (all offline, no model): a temporary e2e spec for the Markdown editor and task lists (removed after);
  `tests/e2e/settings-help.spec.ts` with `--repeat-each=6` (1 worker) and `--repeat-each=10` (4 workers); the risk
  classifier on 50 commands; a WCAG contrast calculation over `web/src/palettes.css`; `bun run build`
  (first-load JS 215.8 KiB gzip in 3 files, budget 228 KiB); `tsc --noUnusedLocals` (clean; it is already on) and an
  unused-export scan (none found); the timings files against the test lists.
- **Not run**: full suites, soak tests, real-model tests, the macOS GUI tests (see §8).

  `code: "cost_cap"`: a per-conversation cap in the session controls and a distinct banner when it is reached.
- **Edit rejections** (18.13.0): `get_session_stats.editRejections` and `details.errorKind` on failed edits: a line in
  the stats panel ("3 edits refused: stale tag ×2, unseen lines ×1").

  `includeReasoning`, `display.advisorCollapsedLines`, exposed in Settings.

  with its artifacts and blobs in omp's own format, and the source copy marked stale so a later resume forks.
