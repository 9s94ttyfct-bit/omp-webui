# Plugins page

## What it does

Manages omp's plugins, skills and MCP servers on the computer omp-webui runs on. Plugins and skills are changed by omp's own CLI (`omp plugin …`, `omp skill …`, run without a shell, in the server's environment: the same HOME and agent directory as the Commands & terminal page), never by editing omp's files; the one exception is a new MCP server (below), for which omp has no command. omp keeps the user's plugins under `~/.omp/plugins` (`installed_plugins.json`, `omp-plugins.lock.json`, `node_modules`) and the marketplaces in `~/.omp/marketplaces.json` with their catalogs under `~/.omp/plugins/cache/marketplaces/`; a project's own plugins are under the project's `.omp/plugins`. Registry skills are listed in `skills.json` / `skills.lock.json` of omp's agent directory (or a project's `.omp`), the user's MCP servers in the agent directory's `mcp.json`.

The page has six tabs (Overview, Plugins, Skills, Marketplaces, Discover, MCP servers); the folder picker and the outcome of the last change are above them.

- **Folder**: omp's CLI runs in the home folder (the user's plugins) or in a project folder chosen from the recent conversations' folders. In a project folder omp lists that project's plugins with the user's, and a marketplace plugin can be installed for the project (scope `project`).
- **Overview** (opens first): how many plugins and skills there are (on / off), how many marketplaces and the plugins their catalogs offer, and how many updates the last check found; each count opens its tab (Updates scrolls to the section). Below it, **Updates** and **Doctor**.
- **Updates** (`server/omp/plugin-updates.ts`): **Check now** first refreshes the marketplaces' catalogs (`omp plugin marketplace update`, when any is added), then looks, for the user (in the home folder) and for each project folder of the stored conversations that has plugins (`.omp/plugins/installed_plugins.json`) or registry skills (`.omp/skills.json`) of its own:
  - marketplace plugins: `omp plugin upgrade --dry-run` (in each folder; only that folder's own scope is taken from it);
  - npm plugins (the user's): `latest` (`<registry>/<name>/latest`, 15 s) from the registry npm and omp would install it from (a scope's registry in `.npmrc` or `bunfig.toml`, else `npm_config_registry`, `.npmrc`'s `registry`, `bunfig.toml`'s, else registry.npmjs.org), with the credentials set for it there, against the installed version, for a plugin installed by name or version range (`~/.omp/plugins/package.json`); one installed from git, a URL or a folder, or one that registry cannot tell of (its answer is the reason), is listed as *not checked* (only reinstalling it, **Upgrade** in the Plugins tab, finds out); a linked folder is skipped;
  - registry skills: `omp skill info <@scope/name> --json` (`distTags.latest`) against the version in omp's skill store.
  Each source is read on its own: one that fails is a line under *Not checked*, the rest are listed. The updates are grouped (plugins, skills), each with its place (user or the project folder), its source and `from → to`; checkboxes (one per update, one per group) choose them. **Update selected (N)** and **Update all (N)** list what will be installed and ask, then run one job of one command per update, in turn, each in its own folder: `omp plugin upgrade <id> --scope <scope>` (marketplace), `omp plugin upgrade <name>` (npm), `omp skill update <@scope/name> [-g]` (registry; a skill that ships scripts fails, since the job has no terminal to ask on: install it again from the Skills tab). A step that fails does not stop the rest; what was installed leaves the list, and open conversations reload once.
  - **Update automatically** (`ompw.extensionsAutoUpdate`, off unless turned on): the server checks a minute after it starts (or after the switch is turned on; at once when the last check is 6 hours old) and every 6 hours, and when something is newer installs all of it once no conversation is working, asking, paused or waiting and no other change runs (looked at again every 30 s; the section says how many conversations it waits for, the next check, and the last automatic install with its count or error). What a check already found when it is turned on, and what **Check now** finds while it is on, is installed the same way. Turned off, it stops and installs nothing it was waiting to. The job it starts shows on the page like any other, marked *Started by the automatic update*.
- **Plugins** tab: one card per plugin and scope, with its version, scope (`user` / `project`), where it came from (the marketplace's name, `npm` for npm and git installs, `folder` for a linked local folder), its description, and a note when the project's copy shadows a user one. Filters by source and on/off appear when the list has more than one value for them.
  - **Switch**: `omp plugin enable|disable [--scope] <id>`.
  - **Upgrade**: `omp plugin upgrade <id> [--scope]` (not offered for a linked folder). A marketplace plugin whose catalog has a newer version shows it (`omp plugin upgrade --dry-run`, read each time the page lists), and the section offers **Upgrade all (N)**, which lists what would be upgraded and asks before running `omp plugin upgrade`.
  - **Uninstall**: asks first, then `omp plugin uninstall <id> [--scope]`. A linked folder is unlinked; the folder itself stays.
  - **Features** (plugins whose manifest declares `omp.features`): checkboxes; Save runs `omp plugin features <name> --set a,b` (or `--disable` all of them when none is ticked). Until the person chooses, omp turns on the features marked default.
  - **Settings** (plugins whose manifest declares `omp.settings`): each setting's key, type, description, the environment variable it is also read from, and its value or default; Save runs `omp plugin config set <name> <key> <value>`, **Reset to default** runs `omp plugin config delete`. A secret setting's value is never sent to a page: it shows only whether it is set.
- **Discover** tab:
  - **Recommended marketplaces** (`shared/plugins-catalogs.ts`, each checked on 2026-11-03 to hold a `.claude-plugin/marketplace.json` under the name listed): plugin marketplaces `anthropics/claude-plugins-official` (official), `anthropics/claude-plugins-community`, `anthropics/knowledge-work-plugins`, `wshobson/agents`, `obra/superpowers-marketplace`, `EveryInc/compound-engineering-plugin`, `jeremylongshore/claude-code-plugins-plus-skills`, `ChromeDevTools/chrome-devtools-mcp`; skill libraries `anthropics/skills`, `trailofbits/skills`, `addyosmani/web-quality-skills`. Each shows *added as <name>* when a configured marketplace has its name or its GitHub repository (`owner/repo`, a GitHub URL, with or without `.git`), else **Add**, which runs `omp plugin marketplace add <owner/repo>` as a job. `anthropics/claude-code` is deprecated and not listed. A link opens claude.com's web catalog.
  - **Catalogs**: every plugin of every added marketplace (`omp plugin discover <marketplace>`), with its version, description, marketplace, and the scopes it is installed in, plus what the marketplace's cached catalog says of it (`~/.omp/marketplaces.json` names each catalog's `marketplace.json`; matched by plugin name, nothing fails when it cannot be read): category, author, homepage, tags and keywords, and how many skills it lists. A text filter (name, description, marketplace, author, category, tags), filters by marketplace, category and installed or not, each choice counted over what the other filters keep (`facets` in `web/src/components/plugins/parts.tsx`), and a sort by name, marketplace or category. **Install** with a scope runs `omp plugin install <name>@<marketplace> --scope <scope>`.
  - **Install from npm, git or a folder**: a package (`name`, `name@1.2.3`, `name[feature]`), `github:user/repo[#ref]`, a git URL, a folder on this computer (`~/…` is taken from the home folder; a folder is linked, so edits in it apply), or `name@marketplace`. The scope applies to marketplace plugins only (omp ignores it for the rest).
- **Skills** tab: every skill omp discovers in the folder (`omp skill list --json`: name, description, where omp found it, `user` / `project`, hidden), on and off (`server/omp/skill-switches.ts`). A skill is off where `skill:<name>` is in omp's `disabledExtensions`: the global list, or a project folder's own list in `<folder>/.omp/config.yml`, which replaces the global one there. `omp skill list` leaves out what the list in force turns off, so the server also lists skills in a folder of its data folder (`skill-probe/`) whose `.omp/config.yml` sets an empty list; a name a list turns off that omp no longer finds is shown as *not found*.
  - **All folders** switch: writes the global list with `omp config set disabledExtensions` (run in the data folder, so no project value is copied into it).
  - **This project** switch (a project folder chosen): writes the folder's `.omp/config.yml` in place, since omp's CLI writes only the global layer. A folder without a list starts from a copy of the global list. Only the top-level `disabledExtensions` lines are replaced; the result is parsed and must keep every other key and read back as the new list, else the file is not touched (409 with the reason). It is written to a temporary file and renamed, then `omp config list --scope project` must read the same list. **Use the global list** takes the key out.
  - Selecting several skills switches them together (one write); filters by source, level and on/off; a skill's path opens its `SKILL.md` read only (only the file omp lists for that skill name, at most 256 KiB).
  - A skill from omp's registry shows its version and **Uninstall** (asks first; `omp skill uninstall <@scope/name> [-g]`). **omp's skill registry** searches skills.omp.sh (`omp skill search <query> --json`), sorts the hits by best match, downloads or name and can hide deprecated ones; **Install** runs `omp skill install <@scope/name> -g` (user) or without `-g` (project). The registry is still small: no hit says so and offers the skill libraries of Discover. omp refuses to install a skill that ships scripts without a terminal to ask on; the page then shows what omp listed (**Review scripts**) and, if the person agrees, runs the install again with `-y`.
  - Running omps watch their config and rediscover skills when it changes; nothing is restarted.
- **MCP servers** tab: searches the official MCP Registry (`GET <registry>/v0/servers?search=<q>&limit=20&version=latest`, fetched by the server with a 15 s timeout and a 2 MiB cap; **More** follows its cursor). Each server shows its title, name, version, description, repository, whether a server in the user's or the folder's `mcp.json` already runs it (*added as <name>*: the same package at any version, or the same address), and its ways of running it, each as the whole command line it writes (every runtime and package argument, the environment in front, `{name}` for a value to fill in) or its address. **Add to omp** opens a dialog: the name in omp's config (the last part of the registry name; one already in the user's `mcp.json` is refused) and the values it needs (environment variables, headers, arguments, `{placeholders}`; secret ones in password fields, defaults as placeholders). The server fetches the entry again from the registry (`/v0/servers/<name>/versions/<version>`), never trusting the page for it, and writes the user's `mcp.json` in omp's agent directory as omp's `/mcp add` does: an npm package as `{ type: "stdio", command: "npx", args: ["-y", "<pkg>@<version>", …], env }`, a PyPI package with `uvx <pkg>@<version>`, an OCI image with `docker run -i --rm [-e NAME…] <image>`, a remote as `{ type: "http" | "sse", url, headers }`. Refused, with why: other package kinds (nuget, cargo, mcpb…), a package from a registry other than npm's or PyPI's public one (also through a runtime argument: `--registry`, `--index-url`, `--extra-index-url`, `--index`, `--find-links`…), a runtime argument that makes `npx` or `uvx` fetch or run something else (`--package`, `--call`, `--from`, `--with`…), a package that serves HTTP itself, a remote transport omp does not speak, a name or value that could be read as something else. Conversations started afterwards connect the server; a running one after a restart. Links to Smithery, Glama and mcp.so (Smithery's API needs a key, so it is not searched).
- **Marketplaces** tab: each added marketplace and its source, **Update** (`omp plugin marketplace update [<name>]`, also **Update all**; with two or more, checkboxes and **Update selected (N)**, one job that updates each chosen marketplace in turn), **Remove** (asks first; plugins installed from it stay installed), and **Add** by `owner/repo`, a git URL or a folder that holds `.omp-plugin/marketplace.json` or `.claude-plugin/marketplace.json`. A marketplace whose catalog cannot be read shows omp's error.
- **Doctor** (in Overview): **Run checks** shows `omp plugin doctor --json` (the plugins folder, its package files, each plugin's manifest and entries, version drift); **Fix** runs `omp plugin doctor --fix` when a check is not ok.

**Progress**: an install, upgrade, uninstall, Fix, every marketplace change and every skill install or uninstall run as a job on the server; the page shows the command, what omp prints as it goes, and omp's own error text when it fails. A switch, features, settings and adding an MCP server answer at once. One change runs at a time (also in turn with the Loaded dialog's switches); while one runs the page's controls wait, and a page opened meanwhile follows it.

**Open conversations**: after a change a conversation loads (anything but a marketplace's catalog), every running Full conversation is told to `/reload-plugins`, and the page lists which reloaded, which need a restart (their omp has no `/reload-plugins`, or it did not answer in 20 s: Restart in the conversation's panel) and which are paused (they see it after Resume and a restart). Light conversations load no plugins and are left alone.

## Where it is

- Sidebar / rail item **Plugins** (`plugins`, `#/plugins`), where Commands & terminal was; also in the command palette's Go to.
- Settings › App & system › **omp configuration** › **Plugins** opens it.
- A conversation's Loaded dialog keeps its own plugin switches (see [session-controls.md](session-controls.md)).

## Settings

One folder of omp-webui's own: `skill-probe/` in its data folder, whose `.omp/config.yml` (`disabledExtensions: []`, written when missing or changed) lets omp list the skills that are off. What the page changes is omp's: its plugin files under `~/.omp/plugins` (or a project's `.omp/plugins`), `~/.omp/marketplaces.json`, its registry skills, the global `disabledExtensions` and a project's `.omp/config.yml` (that key only), and the user's `mcp.json` in omp's agent directory. `OMPW_MCP_REGISTRY` (tests only) points the MCP tab at a stand-in registry.

| Key | Values | Default | Effect |
|---|---|---|---|
| `ompw.extensionsAutoUpdate` | `on`, `off` | unset (off) | Synced preference (the Overview's **Update automatically**). On: the server checks for newer plugins, registry skills and marketplace catalogs a minute after it starts and every 6 hours, and installs everything newer once no conversation is working, asking, paused or waiting. Sensitive: an agent changes it only with the person's Allow. `OMPW_EXTENSIONS_CHECK_MS`, `OMPW_EXTENSIONS_FIRST_CHECK_MS`, `OMPW_EXTENSIONS_RETRY_MS` (tests only) shorten its intervals. |

## API routes

| Route | Methods | Access | Purpose |
|---|---|---|---|
| `/api/plugins` | GET | token | Query `cwd?` (an absolute folder; none: the home folder). `{ cwd, home, installed, marketplaces, catalog, upgradeError }`; each list is `{ error }` on its own when omp could not answer. |
| `/api/plugins/doctor` | GET | token | Query `cwd?`: `{ checks: [{ name, status: ok\|warning\|error, message, fixed? }] }` from `omp plugin doctor --json`. |
| `/api/plugins/config` | GET, POST | token | GET: query `name`, `cwd?`: `{ settings }` (a secret's value is never included). POST `{ name, key, value, cwd? }` (`value` null deletes it): `{ settings, reloads }`. |
| `/api/plugins/enable` | POST | token | `{ id, enabled, scope?, cwd? }`: `omp plugin enable\|disable`. Answers `{ reloads }`. |
| `/api/plugins/features` | POST | token | `{ name, features: string[], cwd? }`: exactly these features on. Answers `{ reloads }`. |
| `/api/plugins/jobs` | GET, POST | token | GET: `{ running }`, the job running now or null. POST `{ action, cwd?, … }` starts one (202 `{ job }`): `install` `{ spec, scope?, force? }`, `uninstall` `{ id, scope? }`, `upgrade` `{ id?, scope? }` (no id: all), `doctor-fix`, `marketplace-add` `{ source }`, `marketplace-remove` `{ name }`, `marketplace-update` `{ name? }` or `{ names: string[] }` (each in turn), `skill-install` `{ spec, scope?, yes? }`, `skill-uninstall` `{ id, scope? }`, `update` `{ keys: string[] \| "all" }` (the last check's updates by `key`; 409 when one is no longer listed). 409 while another change runs or an import writes. |
| `/api/plugins/updates` | GET | token | The last check and the automatic update: `{ checking, checkedAt, updates: [{ key, kind: plugin\|skill, id, source: marketplace\|npm\|registry, scope, folder, from, to }], unchecked: [{ kind, id, scope, folder, reason: git\|error, detail }], errors, folders, auto: { on, nextCheckAt, waitingFor: { working, asking, paused, waiting } \| null, last: { at, count, error } \| null } }`. Kept in memory: a restart forgets it. |
| `/api/plugins/updates/check` | POST | token | Starts a check (202, the state with `checking: true`; a second one while it runs joins it); ask GET until `checking` is false. 409 while an import writes. |
| `/api/plugins/skills` | GET | token | Query `cwd?`: `{ installed: [{ name, description, provider, level, path, hidden, registry: { id, version } \| null, offGlobally, offInProject: boolean \| null, nameOnly }], project, projectList }`. |
| `/api/plugins/skills/enable` | POST | token | `{ names: string[], enabled, scope: global\|project, cwd? }`: those skills on or off in the global list or the project's own. Answers the skills as GET does; 409 for the home folder with `project`, a project file it cannot edit safely, or while an import writes. |
| `/api/plugins/skills/use-global` | POST | token | `{ cwd }`: the project's own `disabledExtensions` taken out. Answers the skills as GET does. |
| `/api/plugins/skills/file` | GET | token | Query `name`, `cwd?`: `{ path, text, cut }`, the `SKILL.md` omp lists for that skill (256 KiB at most); 404 when omp lists none. |
| `/api/plugins/skills/search` | GET | token | Query `q`, `cwd?`: `{ total, hits: [{ id, version, description, weeklyDownloads, publisher, keywords, deprecated }] }` from `omp skill search <q> --json`. |
| `/api/plugins/mcp/search` | GET | token | Query `q?`, `cursor?`, `cwd?`: `{ servers: [{ name, title, description, version, repository, website, options: [{ id, kind, transport, summary, inputs, problem }], configName, added }], nextCursor, taken }`; 502/504 when the registry fails or is slow. |
| `/api/plugins/mcp` | POST | token | `{ server, version, option, name, values, cwd? }`: adds that way of running the server to the user's `mcp.json`; `{ name, file }`. 400 for a bad name or a required value left empty, 404 for a server or option the registry does not have, 409 for a name already there (or a file that is not JSON) or while another change runs, 422 for an option that cannot be mapped. |
| `/api/plugins/jobs/<id>` | GET | token | `{ job: { id, action, command, state: running\|done\|failed, output, error, startedAt, endedAt, reloads, auto? } }` (`command`: one line per command of a job of several; `auto`: started by the automatic update); the last 20 jobs are kept. |

`reloads` is `[{ liveId, sessionFile, state: reloaded\|restart\|paused }]`. A job omp refused because the skill ships scripts has `confirm: "scripts"`. Errors answer `{ error }`: 400 for an argument refused before omp runs, 409 (busy, folder gone, import), 422 with omp's own words when omp failed, 504 when it did not finish in time (30 s for a listing or a quick change, 2 minutes for an uninstall or a removal, 10 minutes for what fetches).

## Limits and caveats

- Every name, spec, source, feature, key and value is checked before it is put on omp's command line: anything that starts with `-` (omp would read it as a flag, and drop one it does not know) or holds a control character is refused, and so is a project scope in the home folder. A setting's value that starts with `-` cannot be set here (omp's CLI cannot take it); use the terminal's `omp plugin config set` with omp's own quoting, or the plugin's environment variable.
- A marketplace plugin has no features or settings omp can switch from its CLI; a linked folder is not upgraded (edit the folder).
- npm and git installs and adding a marketplace from GitHub need the network and `git` / `bun` on this computer; omp prints why when they fail.
- What omp prints is shown as it is (English).

## Security notes

- The routes are open to every page that has the token (not local-only), as the Commands & terminal page is: that page already runs any `omp` command line, `omp plugin` and `omp skill` included, for such a page, and a conversation's `/mcp add` adds any MCP server, so these routes give it nothing more; a change waits while an import writes and runs one at a time. A plugin, a skill with scripts or an MCP server runs code in every later conversation's omp, so adding one is as consequential as running a command; the page adds nothing by itself, and agents must not install, upgrade or remove plugins or skills, or add MCP servers, through this API unless the person asks.
- The automatic update installs only newer versions of what is already installed, from where it was installed (its marketplace, npm, skills.omp.sh), and only while the person has turned it on (`ompw.extensionsAutoUpdate`, sensitive); it never adds anything, and a registry skill whose new version ships scripts is not installed by it (omp needs a terminal to ask). A newer version is new code that every later conversation runs, as an upgrade by hand is.
- A secret setting's value stays on this computer: `/api/plugins/config` answers only whether it is set. An MCP value is written to `mcp.json` (mode 0600) and never sent back, logged or repeated in an error.
- The MCP Registry is fetched by the server only, with a timeout and a size cap; what it says is data (a package name or a value that could be read as a flag is refused), and the entry written is built from the registry's own answer, fetched again on Add.
- omp runs without a shell; nothing the page sends is interpreted by one.
