# The built-in browser

## What it does

omp-webui owns the browser its conversations' agents browse in: **CEF** inside the macOS app, or **Chrome for Testing** (CfT) that the server starts itself when it runs alone. Neither opens a debugging port, and the person's own Chrome is never used.

Every page belongs to one conversation (its session file): a conversation's agent sees and uses only its own pages, and the side panel's **Browser** tab of that conversation lists only those. The agent and the person share that conversation's pages: what the agent opens the person sees, and the person can click and type into it while the agent works.

**The Browser tab** (side panel, lower pane by default):

- the conversation's pages as tabs (each with a close button), and **New page** (+);
- **Back**, **Forward**, **Reload** and an address field: Enter goes to what is typed (`localhost:3000` gets `http://`, anything else without a scheme `https://`). With no page yet, the tab says so and the address field opens one;
- the page size: **Desktop** (laid out at 1280×800 by default, or the size set in Settings › Browser, and shown scaled down to the panel, so the agent's screenshots, the Mac, a browser tab and a phone all show the same layout), **Panel** (laid out at the size of the panel that last changed it) and **Phone** (390×844, as a phone). Phone is a phone to the sites too: the page says it is Chrome on an Android phone (user agent and the client hints `Sec-CH-UA-Mobile: ?1` and `Sec-CH-UA-Platform: "Android"`, the browser's own major version) with touch, and is loaded again when it changes between Phone and the other sizes, so a site that sends phones another page sends that one, not its desktop page squeezed onto 390 px; Desktop and Panel send the browser's own user agent again. The page's layout size is shown beside it;
- the page itself: in a browser tab, on a phone and in the app's windows onto other Macs, a live screencast that takes clicks, taps, the wheel (a finger dragged scrolls), keys and typed or composed text (an IME, a phone's keyboard) in the page's own coordinates. The page takes the keyboard only after the person clicks or taps into it, or Tabs to it (the screen is a tab stop, *Page … — press Enter to type into it*) and presses Enter; it never takes it from the message box by itself. While the page has the keyboard every key is the page's, Tab included, except **Ctrl+F6**, which gives the keyboard back to the screen's tab stop, from where Tab moves on; a hint at the bottom of the page (*Ctrl+F6 to leave*) says so meanwhile. In the Mac app's own windows a native view of the page is laid over the tab instead, and hides while a menu, popover or dialog of the web page is over it;
- **Full screen** and **Open in a new window**, beside the address field. Full screen shows the conversation's browser over the whole window (`#/s/<file>/browser`: Back, **Exit full screen** or Escape leave it — in the Mac app's native view, which has the keyboard once it is clicked, the app tells the page of an Escape (`ompw-native-escape`) and the full screen ends, while the key still goes on to the page; a reload keeps it); a new window shows it and nothing else (`/?popout#/s/<file>/browser`, a native window in the Mac app, which has its own **Full screen** for the window). It starts on the page the tab showed. The browser is shown in one place at a time: while it is full screen or in a window of its own, the side panel's tab says so and offers **Show it here** (which leaves the full screen, or closes the window), and the full screen does the same while it is in a window. The window tells the app's other pages of the same address that it is open (a `BroadcastChannel`, every second, and when it closes);
- the console strip: what the page logs and the requests that fail, read from that page's own session (never another conversation's). **Send to agent** on an error puts `Console error on <url>: <text>` into the message box.

When Chrome for Testing is not installed, the tab says so and offers **Install** to a page that may install it (see Security notes); otherwise it points to Settings › Browser. The Mac app's CEF comes with the app and is never installed. When the browser cannot be used (it failed to start, it restarted), the tab says why.

**Settings › Browser**: **Use the built-in browser** (on by default; off, there is no Browser tab in the side panel, every page of the browser closes, no conversation is given its endpoint and omp's own browser is turned off too, `browser.enabled: false` in each conversation's overlay, so the agents have no browser at all until it is turned on again; only a page that may manage the browser can turn it off or on), the engine this server drives and its version, **Clear browser data** (asks first; removes logins, cookies, storage and the cache: CfT restarts and its pages close; with CEF the app restarts by itself and removes the profile as it starts, and every Browser tab starts empty), a note while the app still has to restart to finish a Clear (the person cancelled the quit question), and **Size of new pages** (width × height of the Desktop layout). With CEF that is all: it comes with the Mac app (*Comes with the app, and is updated with it*), so its version is the one the app was built with and changes when the app updates. With Chrome for Testing the card also has **Update the built-in browser automatically** (on by default; see *Automatic updates* below; only a page that may manage the browser can change it), the newest version known (**Check for a newer version** looks it up), what the last automatic check came to (*Up to date, checked …*, *Version … is downloaded …*, *Updated to …*, *Last check failed (…): …*), **Install** / **Update** (download into the data folder with progress and **Cancel**) and **Uninstall** (asks first; stops it and removes it and its profile now; until it is installed again the conversations' agents use omp's own browser, unless the browser is turned off).

**Automatic updates (Chrome for Testing).** While **Update the built-in browser automatically** is on, the browser is turned on and a version is installed, the server looks for a newer version a minute after it starts and then every 24 hours, where **Update** looks (Chrome for Testing's Stable in Google's last-known-good list). Only a version newer than the installed one is taken. It is downloaded and checked in the background exactly as **Update** does (the card shows the download, which **Cancel** stops), and nothing that runs is touched meanwhile. Chrome for Testing is then switched to it only when no conversation uses the browser: the engine does not run, or no conversation's agent is connected to it, no Browser tab shows one of its pages and nothing used it for five minutes; until then the server looks again every minute. The switch restarts the engine (if it ran) on the new version, so the pages close as with **Update**, and the old version's folder is removed. A failed check or download is written once to the server's log and shown in the card (never as an error message that pops up), and the next check, a day later, tries again. Nothing is looked up while the switch is off, the browser is turned off or nothing is installed, and with `OMP_WEBUI_UPDATE_CHECK=off`. **Update** works as before at any time, and takes a version that an automatic update already downloaded without downloading it again. The Mac app's CEF is not updated by the server: a new CEF comes with a new version of the app.

**How a conversation's agent browses in it.** omp's browser tool is pointed at the built-in browser, never at omp's own hidden Chromium or the person's Chrome. The server writes two lines into the conversation's own settings overlay (the `--config` file omp is started with and reloads when it changes): `browser.cdpUrl`, the conversation's endpoint, and `browser.relay: false`; and it starts every omp with `PI_BROWSER_RELAY=0`, so omp's relay to the person's Chrome is off either way. The endpoint is `http://<token>@127.0.0.1:<port>`: omp asks it for `/json/version` (the token travels as the URL's user name) and is sent on to `/browser-cdp/<token>/devtools/browser`. Each conversation has a token of its own, kept with the page owners in `owners.json` in the data folder; a conversation gets its endpoint once it has a session file, and the server writes it again when it comes up on another port or when the browser is installed. While the browser is not installed no `browser.cdpUrl` is written, and omp uses its own hidden Chromium as before.

**What agents are told.** Every agent of a conversation (the main agent and each subagent) has a note at the end of its system prompt, from omp-webui's docs extension: use omp's browser (the `browser` object in eval, connected to the built-in browser) for every web page (a local HTML file: served on localhost, or set as the page's content), and give it no other browser; `browser.open` attaches to the conversation's current page (every tab name lands on it, and `browser.close` releases it without closing it); another page is opened from the page (a link, `window.open`) or with `tab.run(({ browser }) => browser.newPage())` and attached with `browser.open({ name, app: { target: "<URL or title substring>" } })`; a download is waited for with `tab.waitForDownload()` started before the click in the same `tab.run` (or `downloads: "<folder>"` on `browser.open`), which gives the file's path, and one nobody waits for goes to the browser's default folder (~/Downloads); never show a page in a window on the person's desktop (their Safari, Chrome or Firefox through computer use, `open`, AppleScript or a URL, or a headed Playwright or Puppeteer browser); a test suite's own headless browser is fine; where the browser is turned off, a headless browser of the agent's own, or ask. A conversation started with `--trusted-extension` runs no extension of omp-webui's and has no note.

**What an agent can do there (checked with omp 18.16, v0.18.6).** Every feature of omp's browser tool works through the conversation's endpoint: pages (open, a page's `window.open` and links to a new tab, `browser.newPage()`, adopting one with `app.target`), inspection (`observe`, `ariaSnapshot`, `a11y`, screenshots with `fullPage`, `text`/`html`, console and errors, requests, `route`, HAR, frames, out-of-process iframes included), input (click, type, press, drag, `uploadFile`), downloads, dialogs (`setDialogs`, `handleDialog`), emulation (viewport, devices with touch, geolocation, offline and network throttling, CPU throttling, colour scheme, time zone and locale, headers, user agent), tracing, profiling, metrics, vitals, PDF, recording, cookies, storage, `saveState`/`loadState`, init scripts and WebMCP (the browser runs with Chrome's WebMCP on, so `webmcpList`/`webmcpInvoke` see a page's declared tools). Every page is kept as if it were the active one (on CfT the pages are tabs of one headless window, and all but the newest would be hidden, with no animation frames): an older conversation's page renders and answers as the newest does. Over CEF a download behaviour a session sets is given to every page (each page's channel carries only its own downloads' events), and every page's download events go to each session that asked for them.

What the endpoint lets a conversation see: its own pages only. Target discovery, the target list and attaching see nothing else, and a command that names another conversation's page or session is refused (`Not this conversation's page`). A page the conversation creates, and a page one of its pages opens (`window.open`, a link to a new tab), is that conversation's and shows as another tab of its Browser tab, never as a window. omp attaches to a page that is there rather than making one, so a conversation with no page gets a blank one before its first answer, and that is the page its Browser tab shows. Its own browser target (the browser session its connection is, Puppeteer's `browser.target()`) is told of and can be attached to as a flat session, which omp's downloads use (`Browser.setDownloadBehavior` and the download events); that session is filtered as the first one is, and another connection's browser target is never told of nor attachable. `Browser.close` on any of its sessions ends its own connection, not the browser. Commands about the whole browser (cookies, downloads, permissions) go through: the login state is one, shared by every conversation and the person, and so is where downloads go (the latest folder an agent set, until its tab is released) and who hears of them (a session that asked for download events hears every page's).

Deleting a conversation closes its pages and forgets its token; archiving it closes its pages. A conversation moved to another folder (omp's `/move`) keeps its pages and its endpoint.

**What a session sets on a page ends with it (CEF).** Over CEF every session on a page shares the page's one DevTools channel, so the server remembers, per page, what each session sets that lasts (`Fetch.enable`, `Emulation.set*` such as the size and the user agent, `Network.setExtraHTTPHeaders`, `Page.setInterceptFileChooserDialog`, …: `LASTING` in `server/browser/cef.ts`) and, when that session detaches or its connection ends, gives the page back what the session before it set, or undoes it (`Fetch.disable`, `Emulation.clearDeviceMetricsOverride`, …). A held request goes to the session that holds the interception now. Chrome for Testing gives each session its own state and needs none of this.

**Windows popped out for one conversation.** Each window says over a `BroadcastChannel` that it is open, with an id of its own, and the other pages show the browser in the panel again only when no window of that conversation is open: closing one of two windows leaves it out of the panel until the other one closes (or stops saying so for a few seconds, as a crash does).

**The engines.** Without the Mac app the engine is Chrome for Testing: the server installs it from Settings › Browser and starts it itself, headless, the first time a conversation or a Browser tab needs it, speaking to it over `--remote-debugging-pipe` (Chrome reads and writes CDP on two inherited pipes and opens no port). In the Mac app the engine is CEF, inside the app's own process: the app ships CEF's framework (`omp-webui.app/Contents/Frameworks/Chromium Embedded Framework.framework`, the release the app is built against), starts it at launch, and starts its server with `OMP_WEBUI_BROWSER_ENGINE=cef`. While **Use the built-in browser** is off when the app starts (`ompw.browser: off` in `<data dir>/ui-prefs.json`), the app does not load CEF at all and tells its server so (`OMP_WEBUI_CEF_STARTED=0`); turning the browser on then restarts the app the way Clear does (below), and Settings › Browser says *Restart the app to finish* until it has, or until the browser is turned off again. The app connects to the server's `/browser-engine` WebSocket and, on it, reports its pages and carries each page's DevTools channel; the server answers the browser-level CDP `Target` domain itself from that list, so CEF opens no debugging port either. CEF is loaded once per run of the app, so after Clear the app restarts by itself: the server tells this computer's app, which quits as it does for ⌘Q (without offering Run in Background: while a conversation is still working it asks first, and paused conversations and ones waiting out a usage limit stay) and opens again, deleting the profile before it loads CEF. If the person cancels that question, the app keeps running as it was and Settings › Browser says *Restart the app to finish*. Each engine has a profile of its own: logins are not carried from one engine to the other.

**In the Mac app's own windows.** The app's main window and its pop-outs, while CEF runs, lay CEF's own view of the page over the Browser tab instead of the screencast; one view at a time, in the window whose tab placed it last (a tab of another window that hides or is covered does not take it away, and a window that closes gives it back to the hidden window). The tab tells the app where its page area is, the page's layout size and its size mode, and tells the server the room the view has (`fit`); the server lays the page out at its size (Desktop, Panel, Phone) with a scale that fits it into that room, drawn sharp at the screen's own pixel ratio (a phone keeps its own), and the app places the view there, centred at the top and cut to its size, hides it while a menu, popover or dialog of the web page is over it, and moves it to a hidden window when the tab shows no page (the page keeps running, and other windows still see it through the screencast). The fit ends with the tab that set it (it stops watching, or its socket closes): the page is drawn unscaled for the screencasts again. Closing the window keeps every page running in that hidden window; quitting the app closes them. **Developer tools** there opens CEF's own DevTools window for the page. Browser tabs, phones and windows onto other Macs always show the screencast; a window onto another Mac shows that Mac's browser (its pages, its logins, its `localhost`), never this Mac's. A page takes the keyboard only when clicked: never because it loaded or the agent navigated it.

**Downloads (Mac app).** A file a page downloads, whether the person clicked or the page started it, is saved to the Downloads folder of the Mac the app runs on, with no dialog, under a name no file there has (`report.pdf`, then `report (1).pdf`, …), and is marked as downloaded from the web (quarantine) as Safari marks one. A new tab opened only for a download (a link to a new tab that is a file) goes from the conversation's pages at once. A page closed while its download runs (by the person, an agent, or archiving the conversation) goes from the pages at once too, and the download goes on: CEF reports a download only while its page is open, so the app keeps such a page open, hidden, until its downloads end. The app tells the server how each one goes (`download` on `/browser-engine`, a few times a second at most while it runs). The server keeps the downloads of each conversation (the one whose page started it, or whose page opened that page) in memory until it stops, the newest 50 per conversation (a running one is never dropped), and sends them to that conversation's Browser tabs. A conversation moved to another folder keeps its downloads, and one that is deleted loses them from the list (the files stay); the tabs that show either are sent the new list at once. The tab's toolbar then has a **Downloads** button with how many are running; its list shows each one's name, progress and size, **Cancel** for a running one, and for a finished one **Show in Finder** on a page on this Mac or, on any other page that File transfer lets download, **Download to this device** (`/api/browser/downloads/<id>/file`). When Finder cannot show the file, the page says why in a toast: it is not where it was saved any more (moved or deleted), or Finder's `open -R` failed. A download that starts, finishes or fails while the tab is shown says so in a toast (what changed while the tab was not shown, or its connection was down, does not). A download an agent places (`Browser.setDownloadBehavior`, omp's `waitForDownload`) goes where the agent asked and is listed too. A page is told a download's name, never where it is on the Mac. The ids are the app's CEF run and CEF's number for it, so a download of a CEF that started again is never taken for an earlier one.

## Where it is

- Side panel › **Browser** tab of a conversation (a conversation not saved to a file yet has no pages).
- **Settings › App & system › Browser** (`#/settings/app`), found by the search as *Browser*.

## Settings

| Key | Values | Default | Effect |
|---|---|---|---|
| `ompw.browserSize` | `<width>x<height>`, each 320–3840 CSS px | unset (1280×800) | Synced preference. The Desktop layout size a page gets the first time a Browser tab shows it. |
| `ompw.browser` | `on`, `off` | unset (on) | Synced preference. Off: no Browser tab, every page closed, no endpoint, and `browser.enabled: false` in every conversation's overlay. `/api/prefs` refuses to change it (403) from a page that may not manage the browser. |
| `ompw.browserAutoUpdate` | `on`, `off` | unset (on) | Synced preference, Chrome for Testing only. On: the server looks for a newer browser a minute after it starts and every 24 hours, downloads it in the background and switches to it once no conversation uses the browser. `/api/prefs` refuses to change it (403) from a page that may not manage the browser. |

Other stored values: the engines' files and profiles are in `browser/` of the server's data folder (`cft/<version>/`, `cft-profile/`, `cef-profile/`, `current.json`, which says which Chrome for Testing is installed, the Chrome for Testing version an automatic update downloaded and that waits for the browser to be free (`cftNext`), and holds a CEF Clear that the app carries out when it starts again, and `owners.json`, which page belongs to which conversation and each conversation's endpoint token). Only the installed Chrome for Testing version is kept, and one that waits: the server removes the versions an update replaced. The Mac app keeps no CEF in the data folder; as it starts, it removes the `cef/<version>/` copies that earlier versions of the app downloaded there (about 330 MB each). `browser/` is not moved to another computer (Move to another computer): the new computer installs its own browser and signs in again.

## API routes

| Route | Methods | Access | Purpose |
|---|---|---|---|
| `/api/browser` | GET | token | The install state: `engine` (`cft` or `cef`), `installed` version (with CEF, the one the app ships), `latest`, the running `job` (`install`, `update`, `clear` or `uninstall`, bytes received/total; an automatic update's download is an `update` too), `error`, `restartNeeded`, `autoCheck` (the last automatic check since the server started: `at`, `result` `upToDate`, `waiting`, `updated` or `failed`, `version`, `error`; null before one), and `canManage` (whether this page may install, update, clear and uninstall). |
| `/api/browser/check` | POST | token, and this computer or a verified Access sign-in | Look up the newest version now; answers the state. |
| `/api/browser/install` | POST | token, and this computer or a verified Access sign-in | Install the newest version, or update to it (202; progress comes as `browser_state` on the page's socket). |
| `/api/browser/cancel` | POST | token, and this computer or a verified Access sign-in | Stop an install or update. |
| `/api/browser/clear` | POST | token, and this computer or a verified Access sign-in | Clear the browser's profile (202). |
| `/api/browser/uninstall` | POST | token, and this computer or a verified Access sign-in | Remove Chrome for Testing and its profile (202). |
| `/api/browser/downloads/<id>/file` | GET, HEAD | token; a page that is not on this computer under **File transfer** (not `off`), as the Files tab's downloads | A finished download of the built-in browser, as an attachment: the Files tab's rules (`Range`, no private key or protected place to a page that is neither on this computer nor signed in through Cloudflare Access, the transfer log). 404 for no such download or a file that is gone, 409 for one that has not finished. |

The five POST routes answer 403 with `problem: "browserNotHere"` to any other page. With CEF only `/api/browser/clear` is there; the other four answer 404. The Browser tab talks over its own WebSocket, `/ws/browser` (same sign-in as the page's socket): the page list, console entries, JPEG frames, the conversation's downloads (with whether the page is on this computer) and `download_reveal_failed` (`owner`, the conversation it was asked in, which a tab that watches another one since ignores; `gone`: the file is not there any more, otherwise it could not be looked at or Finder did not show it) from the server; watch, open, close, navigate, size, fit (the Mac app's own view), input, `download_cancel` and `download_reveal` (Show in Finder, only from a page on this computer) from the page.

The browser's own endpoints, outside `/api`:

| Endpoint | Kind | Access | Purpose |
|---|---|---|---|
| `/browser-cdp/<token>/json/version`, `/json`, `/json/list` | GET | this computer only, without an `Origin` header (never a web page), the conversation's token | A conversation's CDP discovery: the browser's version and `webSocketDebuggerUrl`, and the list of its own pages (making a blank one when it has none). 401 for a token that is no conversation's, 403 while the browser is turned off, 503 while the browser cannot be used. |
| `/json/version`, `/json`, `/json/list` | GET | as above, with the token as the URL's user name (HTTP Basic) | The same discovery at the server's root, for the endpoint omp is given (`http://<token>@127.0.0.1:<port>`). |
| `/browser-cdp/<token>/devtools/browser`, `/browser-cdp/<token>/devtools/page/<id>` | WebSocket | as above | The conversation's CDP connection: the whole browser seen as its own pages, or one of its pages. |
| `/browser-engine` | WebSocket | this computer only, without an `Origin` header, only while the engine is CEF, and only with the exact token the app started the server with (`x-omp-webui-token` equal to `OMP_WEBUI_TOKEN`, whatever `OMP_WEBUI_AUTH` says) | The Mac app's CEF: its pages and each page's DevTools channel; the server asks it to make and close pages. |

## Limits and caveats

- One set of pages per conversation, shared by its agent and the person. omp attaches to a page and makes none of its own, so every tab name the agent uses (`main`, `docs`) lands on that conversation's current page; another page is reached with `app.target` (above). `browser.targets()` lists nothing here (omp offers it only for Tern and its relay).
- Limits of omp's tool, the same with any Chrome: the page clipboard is refused to `navigator.clipboard.writeText`, so `clipboardWrite`/`clipboardRead` use omp's own copy (`source: "shim"`; `clipboardCopy`/`clipboardPaste` press the keys in the page); a click that opens a `confirm` or `prompt` returns only when it times out unless `setDialogs` was set first (the dialog is open meanwhile, and `handleDialog` answers it); a recording gets a frame only when the page changes; `emulate` merges, so a device once set stays until the tab is opened again.
- Downloads are the browser's, not a conversation's: while an agent's tab waits for downloads (`Browser.setDownloadBehavior`, which a session sets for the whole browser), every download goes to that agent's folder, the person's clicks in any conversation's page too (each agent's `waitForDownload` gives the right path all the same); while none waits, to the Downloads folder. Without the Mac app (Chrome for Testing) the Browser tab lists no downloads: only the app's CEF tells the server of them. The list is in the server's memory: it is empty again after the server restarts.
- A conversation not saved to a file yet has no pages and no endpoint; until it has one its agent uses omp's own hidden Chromium.
- With CEF, a conversation is given its endpoint only while the app's CEF is connected: when CEF failed to load, its agent uses omp's own hidden Chromium, and the endpoints are given once the app's CEF says hello.
- Pages are not restored after the browser or the app restarts (an update, Clear, quitting the app): every Browser tab starts empty. A restart of the server alone keeps which page is whose and each conversation's endpoint.
- Clear with CEF restarts the app, which stops the conversations that are working (after the quit question) as any quit does.
- The screencast follows what the connection carries: through the tunnel it is less smooth than on this computer.
- A page sized by Settings › Browser is sized when a Browser tab first shows it; a page shown before keeps its size.
- Passkeys (Mac app, CEF): a page that asks for one opens Chrome's *Passkeys & Security Keys* window on the Mac, which offers a QR code to scan with a phone or tablet that has the passkey (Chrome's hybrid sign-in, over Bluetooth) and a USB security key. The window is the Mac's own, so a page used from a browser tab or a phone shows only that it waits. The passkeys of this Mac's iCloud Keychain are not offered: an app may use them for any site only with Apple's managed entitlement `com.apple.developer.web-browser.public-key-credential`, which Apple grants on request to the Account Holder of an organisation's developer account, after review, through a provisioning profile; the app's self-signed identity cannot carry it (Chromium builds without it behave the same). The app's Info.plist has `NSBluetoothAlwaysUsageDescription` for this window: without it macOS ended the whole app (TCC, SIGABRT) the moment a page asked for a passkey, up to v0.22.3.

## Security notes

- Installing, updating and clearing are for a page on this computer or a page signed in through Cloudflare Access with the person's account; a page that holds only the access token (or none, with authentication off) may view and use the Browser tab but not manage the browser. The server decides from the request's own authentication.
- No engine opens a debugging port: CfT is driven over a pipe the server holds, CEF over the app's `/browser-engine` connection. A conversation's endpoint answers only this computer, never a request with an `Origin` (so no web page, through the tunnel or not), and only with a token the server gave a conversation; with it, a conversation reaches only its own pages.
- `/browser-engine` takes only the app that started the server: on this computer, with the app's own token, and only when the server was started for CEF.
- In the Mac app, the view over the Browser tab takes messages only from the main frame of the server's own page in the app's own windows (the main window and its pop-outs).
- Commands about the whole browser are not filtered: any conversation's agent can read or clear the shared cookies, as the person can. An agent that asks omp for another browser in its own call (omp's relay, another CDP address, an app path) is not stopped.
- Downloads come only from Google's storage (CfT, checked against the MD5 Google lists). The Mac app's CEF is in the app, signed with it.
- The engines never use the macOS keychain: CfT runs with `--use-mock-keychain --password-store=basic`, CEF with `--use-mock-keychain`, so macOS never asks for the keychain. The profiles are kept by the data folder's own permissions.
- Chrome's sandbox is kept wherever it works. In the Mac app every CEF helper process (renderer, GPU, network) runs in Chrome's macOS sandbox: it enters it before it loads anything (`macos/cef/helper.mm`), which is why the framework is inside the app, the only place the sandbox lets a helper read. On Linux it needs unprivileged user namespaces, which Ubuntu 23.10 and later (AppArmor), many containers and CI runners refuse: there Chrome for Testing aborts at once ("No usable sandbox!"), and the server starts it again with `--no-sandbox` and logs that it runs without one.
