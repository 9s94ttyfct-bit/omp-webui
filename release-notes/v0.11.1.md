## English

### Fix: the app getting slow and unresponsive after a while (#282, #283, #284, #285, #286, #281)

- Send and Stop no longer stop working in a long conversation. When a reply was larger than 16 MB (opening a very long conversation), the server silently dropped every message queued behind it. Now nothing is dropped: messages wait in order until the page has taken the earlier ones, and a page that can't keep up is reconnected and brought up to date.
- Long goal runs no longer make the app slower and slower. The running turn draws only its latest steps ("Show earlier steps" shows more), and what each streamed message costs no longer grows with the length of the conversation. In a 55 MB conversation, main-thread work per step stays around 100–145 ms instead of climbing past 1.2 s, and Send and Stop answer within 85 ms.
- Send, Stop and Pause always end. If no answer comes, they show "No answer from the server" (after 45 s) or "Connection lost", and a connection that has silently stopped answering is dropped and remade automatically.
- Opening or reconnecting to a long conversation no longer downloads it a second time. The server passes omp's answer on as it arrives instead of decoding and re-encoding it, so opening a 58 MB conversation holds up Send and Stop for about 25 ms instead of about 160 ms.
- The session list no longer slows down while a subagent runs for a long time: a subagent's transcript is read on from where the last read stopped, not from the start on every change.
- The macOS app keeps only the tail of the server's output instead of everything it printed since launch.

### Chat (#279)

- What a `!command` prints appears where you ran it, and stays there after a reload.
- Going Back to a conversation brings back the messages and the place you were reading.
- A search hit among early messages opens with a few messages around it and a "Show later messages" button, instead of loading everything after it.

### Other fixes (#250, #251, #280)

- A conversation whose output the server isn't reading is held back instead of buffering without limit.
- Git status no longer reads a submodule's own git settings.
- A flaky settings-watcher test is now deterministic.

## 中文

### 修复：应用用久了会变卡、点按钮没反应（#282、#283、#284、#285、#286、#281）

- 长对话里“发送”和“停止”不再失灵。原因是：一条回复超过 16 MB 时（打开很长的对话就会这样），服务器会悄悄丢掉排在它后面的所有消息。现在不会再丢任何消息：消息按顺序排队，等页面收完前面的再发；页面实在跟不上时会自动重连并同步到最新。
- 长时间运行的 goal 不再让应用越来越卡。正在运行的回合只绘制最近的步骤（点“显示更早的步骤”可以看更多），每条流式消息的开销也不再随对话变长而增长。在 55 MB 的对话里，每一步的主线程开销保持在约 100–145 毫秒，不再一路涨到 1.2 秒以上；“发送”和“停止”在 85 毫秒内响应。
- “发送”“停止”“暂停”一定会有结果。收不到回应时会显示“服务器 45 秒内没有响应”或“连接已断开”；悄悄失去响应的连接会被自动放弃并重连。
- 打开或重新连接长对话时，不再把整段对话再下载一遍。服务器把 omp 的回答原样转发，不再解码再编码，因此打开 58 MB 的对话只会让“发送”和“停止”延迟约 25 毫秒（原来约 160 毫秒）。
- 子代理长时间运行时，会话列表不再越来越慢：子代理的记录从上次读到的位置接着读，不再每次变化都从头读。
- macOS 应用只保留服务器输出的最后一部分，不再保存启动以来的全部输出。

### 对话（#279）

- `!命令` 的输出显示在你运行它的位置，刷新后仍在。
- 返回上一个对话时，会恢复之前显示的消息和阅读位置。
- 搜索命中较早的消息时，只显示它附近的几条消息和“显示更晚的消息”按钮，不再把后面的内容全部加载出来。

### 其他修复（#250、#251、#280）

- 服务器来不及读取某个对话的输出时，会让它暂停输出，不再无限制地缓存。
- Git 状态检查不再读取子模块自己的 git 设置。
- 一个时好时坏的设置监视测试现在结果稳定。
