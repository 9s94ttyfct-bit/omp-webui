### Unattended mode and the Questions list (#646)

- The moon switch beside the message box (also in *New chat*'s footer) turns **one conversation** unattended. Settings › **Unattended mode** decides whether a conversation started from *New chat* begins unattended (*Turn it on for new conversations*, off by default) and holds **what the agent is told** (at most 4,000 characters, with *Restore default*, and *Edited* or *As shipped* beside it); the text is changed on this computer only — a page that came through the tunnel or the network is refused with a 403 — and applies from the conversation's next turn.
- While the mode is on, the main agent is told you are away: do not ask you directly, do not wait, go on with everything that does not need a decision, and file what does — a choice between approaches, a missing detail, a permission it is unsure of — with its tool `file_question`: a title, the context you need to answer it, the options it sees (the one it would pick marked) and what it is doing meanwhile. The tool **returns at once**, so the turn never blocks; the agent then does what does not depend on the answer, says what is waiting in a final message, and the answer reaches it later as a message that begins *Answer to your question*. The shipped instruction says exactly that, and that `ask` is only recorded while you are away.
- omp's own `ask` dialog of an unattended conversation (the main agent's or a subagent's) is answered by the server with a fixed *recorded for the person; continue with what does not need the answer* and filed the same way, so a turn never stops on it. **The guard's and the permission prompts are never answered for you**: only `ask` gets the fixed reply, while `select`, `confirm`, `input` and `editor` — every tool approval, and what *Guard dangerous commands* asks — are left as they are and wait exactly as without the mode; a contract test holds the guard's own question to never being answered for the person.
- The sidebar's **Questions** entry (`#/questions`, a lazy chunk whose strings are a chunk of their own; the narrow rail carries the same entry without a number) shows how many wait. The page has *Open (N)* and *Done*, and a filter to every conversation or to one (the chip *N open* beside a conversation's message box opens just that conversation's). A question opens to its context, its options and a box for words; **Answer** sends it as an ordinary message to that conversation — queued behind the turn while it is working, starting a turn while it is idle, opening a conversation that is closed — and the question is marked answered only once the message is on its way: an answer that cannot be sent leaves it open, and a settled one is not answered twice (409). **Dismiss** tells the agent nothing. Turning the mode off leaves the questions in the list.
- What is kept: `questions.json` and `unattended.json` in the app's data folder — private (0600), written whole and moved into place, read again when another server changed them — so questions survive a reload and a restart and travel with *Move to another computer* (a merge import adds the archive's questions by id, never replacing yours). At most 200 are kept (answered and dismissed ones go first), 60 may be open per conversation, every field is cut to its limit, and a questions file larger than 32 MiB — above the largest honest one — is kept aside as damaged.
- How it reaches omp: an extension of the app's own (`server/omp/unattended/`, a sibling of the model guidance's) is installed into the data folder and passed with `--extension`. Its `before_agent_start` handler appends the instruction to the **main** agent's system prompt only, and `file_question` is registered inactive, made available only while the mode is on. The text is a file beside the conversation's settings overlay read at each turn, so a switch reaches the next turn without a restart and compaction or resuming cannot drop it. Its `<file>.loaded` note is what lets the page say the process carries the mode; a conversation started with your own `--trusted-extension` cannot combine it, and the switch says so — while its own `ask` is still filed. Its own questions are the server's to file (the process holds no credential and cannot reach the data).
- A page that is not on this computer may answer and turn the mode on or off — it is you leaving the desk — under the rules every remote message obeys; only the instruction text is this computer's.
- **It says so when a question could not be kept (#650).** `file_question` answers *Recorded* before the server files it, and an `ask` dialog is answered the same way, so nothing may make the turn wait or retry; but when the list could not keep the question — the conversation already had its 60 open, the call named no question, or `questions.json` could not be written — that used to be a console line and a lost question. It is now the conversation's own state (`LiveInfo.questionDropped`): the lazy transcript draws a warning row that names the question and the reason, and a toast, and because it is state rather than a frame a page that attaches later, or was not listening, shows it too. The Questions page keeps a short line under the conversation for each one, so the count of what was lost is there even if no page was open when it happened. The model is still told it was recorded and goes on (it must not wait). The drops are the server's memory only — never the questions file, at most 50 of them — and the notice is cleared when a question is kept. The follow-up left the first load exactly as main's: 202.5 KiB gzip in 3 files, app chunk 237,813 bytes, because the row and its words are in lazy chunks and `shared/unattended.ts` is lazy again.
- Tests: `tests/unit/unattended.test.ts` (39) and `tests/unit/question-dropped.test.ts` (2) — 41 pass; `tests/contract/unattended.test.ts` (8) and `tests/contract/unattended-answer.test.ts` (8) — 16 pass against the real omp (the instruction and the tool in the main agent's request and no subagent's, a filed question, the 61st open question, an `ask` dialog answered, the switch reaching the next turn, the guard's question left alone, an answer to an idle, working and closed conversation, a refusal, a dismissal, a remote page, an edited instruction and *Restore default*, the files' 0600 and a restart); `tests/e2e/unattended.spec.ts` (11: English and Chinese, the Settings card, the warning row and the list's line, and a phone at 390 × 844 with axe and 44 px targets, nothing running off the screen sideways).

### Sleep: keep the Mac awake while a conversation works, and say what a sleep interrupted (#647)

- **A change in behaviour.** The Mac no longer goes to *idle* sleep while a conversation works. Settings › **Sleep** has *Keep the Mac awake while a conversation works* (`ompw.keepAwake`), on unless you turn it off, and it takes effect at once: turned off while a turn runs, `caffeinate` ends there and then; turned on, one starts with what is working.
- How it is done: from the moment the working count goes above zero — the same count the menu bar icon and the app's notifications use — the server runs `/usr/bin/caffeinate -i -w <its own pid>` from an argument list (never a shell), one child at a time, and ends it when the count returns to zero and at its own exit (`-w` ends it even if the server is killed outright). Only idle sleep is held off: the display may still sleep (`-i`), and closing the lid still sleeps the Mac (macOS's own rule, short of clamshell mode on power with a display). A `caffeinate` that dies on its own is started again while anything works. A server that is not on macOS has no `caffeinate`: `/api/meta` answers `keepAwakeAvailable: false` and the card says the setting is not available there rather than showing a switch that would do nothing. The setting is this computer's — `/api/prefs` answers 403 for that key from a page that is not on it, while the other preferences from the same page still go through — and the card is read-only there.
- A conversation waiting out a usage limit does not hold the Mac awake (`awakeWorking`, `server/sleep.ts`) although the menu bar still counts it (its turn is open, and the count there is untouched); a short 5xx backoff does, and so does a continuing goal run unless that pause is the long wait.
- **What a sleep interrupted.** Once a second the server compares its wall clock with `performance.now`, which on Apple platforms is `CLOCK_UPTIME_RAW` and does not advance across a sleep, and a gap of at least 30 seconds that the monotonic clock did not count is a sleep, with its start and end. `process.hrtime` (`mach_continuous_time`) does count through it, so it is a third reading that tells a real sleep from a wall clock moved forward — and a moved clock is not a sleep. Every conversation that was working at the last tick before the gap gets a line in its transcript — *Interrupted while the Mac slept (14:02–15:40)*, a 24-hour clock in both languages — and the next minute of that conversation is followed for the second line: omp retried the turn by itself, the turn ended with an error (Retry is offered as always), or a tool ran out of time on the way back. Nothing is resent on your behalf.
- The note is the conversation's own state (`LiveInfo.slept`), so a page that attaches after the wake, or reloads, shows it; and the watching ending after a minute does not take the line away — it stays until the conversation turns again, ends, or sleeps again (a server restart loses it: it is not in the parked record). The first load carries only the preference key and its validator.
- Settings' search finds the Sleep card by its name, the sentence under it and the words people use for it (aliases include sleep, awake, caffeinate, idle, lid, wake) and opens it.
- Tests: `tests/unit/sleep-decision.test.ts` (37) and `tests/unit/sleep-note.test.ts` (10) — 47 pass; `tests/contract/sleep.test.ts` (6 pass: the real spawner with a stub `caffeinate` started and let go, the setting off ending it at once and on starting one, a server that stops taking it along, a usage-limit wait against a short backoff, a server elsewhere, and a remote page refused the key while its other preferences are taken); `tests/e2e/sleep-note.spec.ts` (5: the line and its second line's three answers, Chinese, the card found by search, and a remote page reading it).

### 无人值守模式与“问题”列表（#646）

- 输入框旁的月亮开关（“新建对话”的底部也有）让**一个对话**进入无人值守。设置 › **无人值守模式** 决定从“新建对话”开始的对话是否一开始就是无人值守（*为新对话打开*，默认关闭），并保存**代理被告知的内容**（最多 4,000 个字符，带“恢复默认”，旁边显示“已编辑”或“随包附带”）；这段文字只能在这台电脑上修改——经隧道或网络地址打开的页面会被 403 拒绝——并从对话的下一轮起生效。
- 模式开着时，主代理被告知你不在：不要直接问你、不要等答复、继续做不需要决定的事；需要你决定的事——方案取舍、缺少的信息、拿不准的权限——用它的工具 `file_question` 记下来：标题、你需要知道才能回答的背景、它看到的选项（会标出它会选的那个）以及它同时在做什么。工具**立刻返回**，所以这一轮从不卡住；代理随后继续做不依赖答案的部分，在最后一条消息里说明还剩什么在等，答案稍后以一条以*Answer to your question*（“回答你的问题”）开头的消息到达。随包附带的说明写的就是这些，也写明你不在时 `ask` 只会被记录。
- 无人值守对话里 omp 自己的 `ask` 对话框（主代理的或子代理的）由服务器用固定的一句*已为对方记录；继续做不需要答案的部分*回复，并同样记成一个问题，所以一轮永远不会因为它停下。**防护和权限询问绝不代答**：只有 `ask` 会得到那句固定回复，而 `select`、`confirm`、`input`、`editor`——所有工具批准，以及*看守危险命令*提出的问题——保持原样，和没有这个模式时一样等你；一个契约测试要求防护自己提出的问题永远不会被代答。
- 侧边栏的**问题**入口（`#/questions`，一个懒加载的代码块，文字自成一个代码块；窄栏里是同样的入口，不带数字）显示有多少个在等。页面有*待回答（N）*和*已处理*两个标签，以及一个筛选器（所有对话或某一个；对话输入框旁的*N 个待回答*只打开这个对话的那些）。打开一个问题能看到它的背景、它的选项和一个写字的框；**回答**把它作为一条普通消息发给那个对话——对话在工作时排在它这一轮后面，空闲时开始新的一轮，已关闭的对话会为它打开——只有消息已经在路上才把问题标为已回答：发不出去的答案会让它继续待回答，已处理的问题不能再回答一次（409）。**忽略**什么都不告诉代理。关掉模式后，问题仍留在列表里。
- 保留什么：应用数据文件夹里的 `questions.json` 和 `unattended.json`——私有（0600），整份写出再移动到位，另一个服务器改过就重新读取——所以问题能熬过重新载入和重启，也随*搬到另一台电脑*一起走（合并导入按 id 把压缩包里的问题加进来，不会替换你的）。最多保留 200 个（先丢已回答和已忽略的），每个对话最多 60 个待回答，每段文字都按上限截断；超过 32 MiB 的问题文件——高于最诚实的文件可能的体积——会被当作损坏留在一边。
- 它怎么到达 omp：一个应用自己的扩展（`server/omp/unattended/`，和模型指引的是兄弟）装进数据文件夹，用 `--extension` 传进去。它的 `before_agent_start` 处理函数只把说明追加到**主**代理的系统提示词后面，`file_question` 注册时是不启用的，只有模式开着才可用。文字是对话设置覆盖文件旁边的一个文件，每一轮都读，所以开关不用重启就到达下一轮，压缩和恢复也丢不掉。它的 `<文件>.loaded` 说明是页面据以说这个进程带着模式的依据；用你自己 `--trusted-extension` 启动的对话不能和它并用，开关会说明这一点——而它自己提出的问题仍会被记下。它自己提出的问题由服务器来保存（进程里没有凭据，也碰不到数据）。
- 不在本机的页面也能回答、也能开关模式——那正是你离开桌子的时刻——遵守每一条远程消息的规则；只有说明文字是这台电脑的。
- **没能保存的问题也会说明（#650）。** `file_question` 在服务器保存之前就回答*已记录*，`ask` 对话框也一样，所以任何东西都不能让这一轮等待或重试；但列表没能保存时——这个对话已有 60 个待回答、调用里没写问题、或 `questions.json` 写不进去——以前只是一行控制台输出，问题就丢了。现在这成了对话自己的状态（`LiveInfo.questionDropped`）：懒加载的转写画出警告行，写明是哪个问题、为什么没保存，并弹一个提示；因为它是状态而不是一帧，晚到的或没在听的页面也看得到。“问题”页面在对话下面为每一个留一行，所以即使当时没有页面打开，丢了多少也看得到。模型仍然被告知“已记录”并继续（它不能等）。这些记录只在服务器的内存里——从不写进问题文件，最多 50 条——保存成功时清除。这次收尾让首屏加载和 main 完全一样：202.5 KiB gzip、3 个文件、app 代码块 237,813 字节，因为警告行和它的文字都在懒加载的代码块里，`shared/unattended.ts` 也重新变懒了。
- 测试：`tests/unit/unattended.test.ts`（39 个）和 `tests/unit/question-dropped.test.ts`（2 个）——41 个通过；`tests/contract/unattended.test.ts`（8 个）和 `tests/contract/unattended-answer.test.ts`（8 个）——对着真实 omp 16 个通过（说明和工具出现在主代理的请求里而不在任何子代理的请求里、记下一个问题、第 61 个待回答的问题、`ask` 对话框被代答、开关到达下一轮、防护自己的问题不被碰、对空闲/工作中/已关闭对话的回答、一次拒绝、一次忽略、一个远程页面、改过的说明和“恢复默认”、文件的 0600 和一次重启）；`tests/e2e/unattended.spec.ts`（11 个：中英文、设置卡片、警告行和列表里的那一行，以及 390 × 844 的手机上带 axe 和 44 px 的点击目标、页面不会横向溢出）。

### 睡眠：对话工作时不让 Mac 进入闲置休眠，并说明休眠打断了什么（#647）

- **行为变化。** 有对话在工作时，Mac 不再进入*闲置*休眠。设置 › **睡眠** 里有*对话工作时不让 Mac 进入休眠*（`ompw.keepAwake`），除非你关掉，默认开启，而且立即生效：在一轮工作进行时关掉，`caffeinate` 会在当时就结束；再打开，就会为一个正在工作的对话启动一个。
- 它是怎么做的：工作计数（菜单栏图标和通知用的就是它）一旦大于零，服务器就以参数数组（绝不经由 shell）运行 `/usr/bin/caffeinate -i -w <自己的 pid>`，一次只有一个子进程，计数回到零时结束它，服务器退出时也结束它（即使服务器被强行杀掉，`-w` 也会让它结束）。只管住闲置休眠：显示器仍可休眠（`-i`），合上盖子也仍会让 Mac 休眠（macOS 自己的规则，通电且接着显示器时的合盖模式除外）。自己意外结束的 `caffeinate` 会在还有东西工作时重新启动。不是 macOS 的服务器没有 `caffeinate`：`/api/meta` 回答 `keepAwakeAvailable: false`，卡片会说明这台机器上不可用，而不是给一个什么也不做的开关。这个设置属于这台电脑——不在本机的页面对这个键会得到 403，同一页面改其他偏好仍然可以通过——那张卡片在那里是只读的。
- 在等用量上限的对话不会让 Mac 保持唤醒（`awakeWorking`，`server/sleep.ts`），虽然菜单栏仍把它算作在工作（它的这一轮是开着的，那里的计数不变）；短暂的 5xx 退避会，正在继续的目标运行也会，除非那次暂停正是那段长时间等待。
- **休眠打断了什么。** 服务器每秒比较一次墙钟和 `performance.now`（在 Apple 平台上它是 `CLOCK_UPTIME_RAW`，跨休眠不前进），间隔至少 30 秒、且单调时钟没有计算的部分就是一次休眠，连同它的开始和结束。`process.hrtime`（`mach_continuous_time`）会照常计算休眠，所以它是第三个读数，用来区分真正的休眠和被往前的墙钟——被往前的钟不算休眠。最后一个 tick 时还在工作的每个对话，转写里会有一行——*Mac 休眠期间被中断（14:02–15:40）*，两种语言都是 24 小时制——随后那一分钟会被跟着看完，补上第二行：omp 自己重试了这一轮、这一轮以错误结束（照旧提供“重试”）、或有个工具在回来时已经超时。你这边什么都不重发。
- 这条记录是对话自己的状态（`LiveInfo.slept`），所以唤醒后才打开或重新载入的页面也看得到；一分钟的观察结束也不会把这一行拿走——它留到对话再次开一轮、结束，或再次休眠（服务器重启会丢掉它：它不在暂停记录里）。首屏只多了偏好键和它的校验。
- 设置里的搜索能按名字、下面那句话和人们的叫法找到睡眠这张卡片（别名包括 sleep、awake、caffeinate、idle、lid、wake），并打开它。

### 修复与开发（#648、#649）

- **#648：模型指引的契约测试偶尔选中了子代理的请求。** v0.11.14 发布时那次没通过，是测试自己的问题，不是 omp 或扩展的：`after` 取的是最近一条说了 `SCOUT-DONE` 并且提供 task 工具的请求，而子代理自己的请求两样都有（它重复自己的任务，omp 也给它 task 工具），所以在子代理的请求和主代理的下一条之间那几毫秒里，选出的是子代理的请求——它本来就不该带指引。把子代理的回答按住 1.5 秒，旧测试每次都会失败，`after` 正是子代理的请求；而带着汇报的那条主代理请求，追到的每一次（并行负载下 36 次，加上按住的那几次）都带着指引。现在汇报用的是任务里从不出现的词（`SCOUT-REPORT-648`），`mainRequestFor` 只接受一条请求必须带的标记、绝不返回子代理的请求；两个测试会按住子代理（或主代理的回答），让汇报在主代理这一轮结束之后、或还在进行时到达，而不是听凭一次运行的时序。把轮询改成 25 毫秒后还发现，第三个测试和恢复测试把下一条提示词发进了还在运行的一轮——旧的 250 毫秒等待把它藏住了（omp 会回答“Agent is already processing”）——所以它们先等到整段第一次交换结束（`idle`：不在流式输出、没有异步工作）。契约测试仍然严格。README（中英文）现在写明了用 omp 18.12.6 实测的结果：子代理汇报开启的那一轮，omp 不运行 `before_agent_start`，所以子代理还在工作时开启或关闭的指引，从你发的下一条提示词起才到达模型，而对话原本带着的指引会继续出现在这些轮里；无人值守的说明走同一个钩子，所以这个模式也一样，`file_question` 也在同一时刻提供或撤掉。`tests/contract/model-guidance.test.ts`：8 个通过。
- **#649：往 omp 的 `config.yml` 里加键的端到端测试改走 `withYaml`**（`tests/support/config-yml.ts`）。omp 写这个文件时结尾没有换行，而一次清空文件的 `omp config reset` 会把它留成 `{}`；接在后面的文字因此不是 omp 能读的 YAML（`thresholdPercent: 80mnemopi:`、`{}mnemopi:`），omp 会把文件挪到一边，于是跑在一次用过 `omp config` 的测试之后的那个测试，自己写的设置一条也没生效——也就是 #649 记下的那次失败的样子。现在这段文字单独占一行，接在文件原有内容之后，`{}` 和空文件也照应到了。改到的测试：`tests/e2e/default-star.spec.ts`、`memory.spec.ts`、`session-defaults.spec.ts`、`slow-mode-claude.spec.ts`。
