### Run in Background (#627)

- **A change in behaviour.** Run in Background now leaves the app with no window at all (`macos/background.swift`, `macos/mainwindow.swift`, `runInBackground` in `macos/main.swift`), where it used to keep a transparent window ordered in. The window is closed and the page in it released — the `WKWebView` and its web content process go with it — so nothing of the app is in Stage Manager, ⌘-Tab or the Dock, and closing another app's last window can no longer bring one back. The app stops being a regular one (`NSApp.setActivationPolicy(.accessory)`): no Dock icon, and the system never makes it the active app. The server, every conversation (working, paused, waiting) and remote access (the tunnel) go on; the app holds an activity assertion so macOS does not nap it (the Mac may still sleep). A subagent's pop-outs and the windows onto other Macs are closed; a window in native full screen leaves it first (3 s at most) and a minimised one is closed as it is; a second Run in Background meanwhile changes nothing, and opening the window again while the app waits for the page cancels it.
- **What is left of the app** is its icon in the menu bar: an `NSStatusItem` with a template image, so the bar colours it, and the number of conversations that wait for an answer beside it while any does. Its menu has *Open omp-webui*, a line saying how many conversations are working and how many need your input (the server counts them; one that waits is not also counted as working) and *Quit omp-webui*, which is the app's quit: the same question as ⌘Q (Quit / Cancel, Cancel / Quit Anyway while something works, none while nothing would be stopped or left), and Cancel leaves the app in the background with the screen given back. The window comes back with a Dock icon and a fresh page from Open, from a click on a notification (the page opens on that conversation) and from opening the app again (Finder, Launchpad, a second copy); nothing else brings it back, activating the app included.
- **Unsent drafts and the view** survive the window going away. The page mirrors its drafts to its session storage (`ompw.drafts`, which dies with the page) and the open conversation is only in `location.hash`; before the window closes the app reads both with a script (1.5 s at most; a page that does not answer keeps nothing), puts the drafts back in the new page's session storage before any of its scripts run (a user script at document start, only where the page has written none) and appends the view to its address, so a message being typed, a pasted picture and the conversation that was open are there again. The drafts are put back **once per web view** (`restoreDraftsScript` sets `ompw.draftsRestored` first): without that marker a reload (⌘R, a crashed web content process, the reload after a server restart) would put a draft back that had already been sent.
- **Terminals keep running.** The server kills a page's terminals when its socket closes, so the app first tells it that this close is on purpose (`POST /api/shell/background`, local-only, answered or waited for 1.5 s at most) and the server's `PtyManager` keeps the terminals of the page that closes next, with the tail of what they printed (256 KiB; they go on running meanwhile), for the page that opens again: the terminal view asks `pty_held` and takes the terminal over with `pty_attach`. A terminal nobody takes over is ended after 24 hours, or with the server. The notice is used up by the first page that leaves terminals, only a page of this computer's leaves any, and it is withdrawn (`DELETE`, local-only like the POST) when the window is opened again before it closed or within its 10 s, so a browser tab of this computer that closes then is not taken for the app's window.
- **Notifications come from the app, not from the page** (#627). With no page in the background, the page cannot be what hears the conversations: the server decides what is worth a notification and the app shows it. `GET /api/shell/events` (`server/shell-events.ts`) is one response that does not end, of newline-delimited JSON, which the app reads from the moment its server is up (`macos/shellevents.swift`: with the app's token, again after the connection breaks or the server starts again, and an empty line every 15 s so that a response gone quiet is noticed). `{ "t": "state", "epoch", "working", "asking" }` is the menu bar icon's counts, said first and whenever either changes; `{ "t": "attention", "seq", "id", "kind", "title", "body", "liveId", "file" }` is a conversation that needs someone: `asking` (a dialog waits) or `finished` (the run ended; for a goal, the whole run). The rules are the page's own rules, now in one place (`shared/attention.ts`, which the tab's title and a browser's notifications use too), the words are the page's words, and the language is the saved one. Nothing is told about an error or a usage limit as such: a turn that ends, however it ends, is `finished`. It is on only while Settings › Notifications is on, and the route is local-only, so a page that came through the tunnel or over a network address is refused it. **A gap does not lose a notice**: once an app has read, the server keeps the last 20 notices with a number (`seq`, from 1 in each run of the server, named by `epoch`), and the app asks for what it missed after a stall, a restart of the connection or being let go for lagging. The app shows a banner (one per conversation: a newer one replaces it) when macOS allows notifications and nobody is looking at the window, and a click opens the window on that conversation. The page no longer notifies in the app at all (`shellShow` and the `parked` event are gone); a browser's page is unchanged.
- **Titles are made by the server** (`server/auto-title.ts`): `/rename` once after a conversation's first exchange, whether a page is open on it or not, so a conversation that finishes while no window is open is named all the same (a title model that gives nothing is asked twice more, and again when another turn ends). Settings, or `OMP_WEBUI_AUTO_TITLE=off`, turns it off.
- **The guard's question still reaches you.** With no page open on a conversation, *Guard dangerous commands* (no reviewer reachable, and *ask me* on) asks the person as long as the app runs in the background with notifications on (`GuardHooks.reachable`): the call waits, the app shows *Needs your input* and the menu bar counts it, and the window the notification opens shows the question. With neither a page nor the app the call is refused for want of a reviewer, as it always was. Closing the window releases idle conversations like closing a browser tab does: the idle reaper ends an omp that has been idle for 15 minutes, and a conversation that works, waits for an answer or is paused is never reaped.

### Changes (#630)

- The *Files* tab has a switch, **Files | Changes** — a switch inside the tab, not a tab of its own; its code is loaded when you first choose it, and nothing is asked of the server before. Changes is **read only by decision**: it shows how the conversation's folder differs from its repository's last commit and offers no stage, commit, restore or discard.
- *Working tree* lists every changed file with the branch, its state (modified, new, deleted, renamed, type changed, untracked, conflict), whether some of the change is staged, and the lines added and removed (not for a binary file, a very large one or an untracked one); a click opens that file's change, drawn **unified** (old and new line numbers, a sign and a tint, never colour alone) or, where the panel is at least 520 px wide, **side by side**, coloured by the file's language, and the choice is kept for every file. *By turn* lists, for each turn, the files omp's `edit` and `write` calls changed (a call that failed changed nothing), newest turn first, each linking to its change, and says when a file no longer differs from the last commit; what a command such as `bash` changed is in the working tree list.
- A new file is shown as all added; a picture, a binary file, a file git does not compare as text (over 1 MiB) and a link say so instead of drawing lines, and a link is never followed. The limits: 500 files listed, 5000 rows and 4000 characters per row of a diff (the page says when it cut, and a long diff draws its first 400 rows with a button for the rest).
- **What is run**: only `git status` and `git diff` for the folder the conversation is in, on the server, with no hooks, no file-system monitor, no external diff program, no text conversion, no pager, no prompt and no fetch from a remote; the page names the conversation and a path, never anything else, so a path the list does not name is not found. A repository whose own settings name a program for git to run, or send git to another work tree (`core.worktree`), or whose top is not the folder or one above it, is not looked at and the view says so; a repository git answers with an error for is said to be **unreadable**, which is not the same as not being a repository. What git prints is read to 4 MiB for the list and 2 MiB for one file's change: past that git is stopped and what was read is shown, marked as cut. A repository inside the folder is one entry, shown with a slash at its end. On a page that is not this computer's, files that are hidden by default or look like secrets are neither named nor shown (the count is said), and a diff that holds a private key is refused, as in the Files tab.

### Side questions (#633)

- **A change in behaviour.** A side question (the *Ask* tab, omp's `/btw`) can be answered by a model of your choosing, and when it is, the answer is not omp's own. The choice sits above the question box and is one for the whole app, not per conversation: kept with the other preferences (`ompw.btwModel`) and shown in every open page as it is made. The default, *omp default*, leaves it to omp: the conversation's own model answers, exactly as `/btw` does. Any page that is connected, a remote one too, can change the choice (it is an app-wide preference like the theme).
- omp's `btw` takes no model (it answers with the session's model), and changing the conversation's model around a question would change the conversation, its transcript and its next turn. So with another model chosen the server answers in a **separate omp process**: it copies the conversation's session file as it is at that moment into a private folder of the data dir (`btw-fork/`, 0700 folder and 0600 files), starts `omp --mode rpc --resume <the copy> --model <the choice>` in the conversation's folder with the conversation's own command line, the same `--config` overlay and the same gate, sends it `btw`, streams the answer into the same list and ends the process; the copy is removed when it has ended, and what a killed server left is removed at the next start. The conversation, its model and its file are not touched, and the main agent's next turn runs on the conversation's own model. Every answer says *Answered by …*. Offline mode: only models of the backend the conversation runs on can be chosen; any other is answered by the conversation's own model, and the panel says so.
- **How it differs from omp's own answer**: it sees the conversation as it is saved, so not a turn that is still streaming (omp's own answer includes it), and a conversation with no file yet (a new chat before its first message) is answered without its context; it costs a process start (omp and its MCP servers); one question of a conversation runs at a time and the next waits (a conversation keeps at most two waiting, a third is refused with a message, and at most three of these processes run at once for all conversations together); a follow-up goes on with the model its topic began on, and a follow-up of a topic omp itself answered stays with omp; and these answers are kept by the server while it runs (30 per conversation, 30 conversations), not in omp's own side-question history that the TUI's `/btw` lists. omp records every session file it opens in `<agent dir>/custom-session-files/`, so each question leaves two small markers there (`gc --stale` removes them once the file they name is gone). Because the whole conversation as far as it is saved goes to the chosen model's provider, the README says so where the choice is described. The compat table records that omp's `btw` takes no model and what is run in its place.

### Export (#632)

- **A change in behaviour.** Export is now a choice: in the Export card each data category (conversations, prompt history, memories, settings, customization, plugins, this app's data) has a checkbox with its files and size beside it, all ticked at first, and the total and the note about secret values left blank count only what is ticked. **Logins** is not a checkbox: it stays the switch below with its password, off by default, with its warning. With nothing ticked and no logins, **Export** is disabled and says why.
- The server exports only the chosen categories: `categories` in the request is a list of data category ids (left out, all seven); a request that names `credentials`, a category there is none of, or something that is not a list is refused with a 400 (`migrateCategories`), and one that names nothing with a 400 (`migrateNothingChosen`), before anything starts. A file that is a secret by its name (`.env`, a key) goes with the category of the folder it lies in, so with only *Settings* ticked and logins on the `.env` of a skill does not go in.
- The manifest records the categories the file holds (`categories`, with `credentials` only when the encrypted part is there), and the finished export says them too; with *Memories* ticked and the conversations or the prompt history not, it also records the folders the memory banks are named after (`bankFolders`, only those that match a bank of the file). On import the preview lists only the categories the file holds and says the rest of this Mac is left exactly as it is; the import writes only the manifest's entries, and the files of the encrypted part only to the places of a category the file holds (a secret by its name also needs the category of its folder), so every other category is byte for byte as it was — idle conversation processes are closed only when omp's files are about to be written. An entry whose path is in a category the manifest does not list makes the file damaged, and nothing is written; a file whose manifest records no categories (made before this) is a whole export and imports as it did.
- What to know of a subset: the lists in this app's data (archived, permission choices, pins) name conversations by their file, so without *Conversations* they name files this Mac does not have; and without *Conversations* the `--session-dir` folders in `session-roots.json` are not moved to this app's own folder, only their old home folder is replaced by this Mac's.

### Subagents (#594)

- A subagent that waits to retry shows in the Agents tab the time omp retries at and a countdown; once omp is 30 seconds past its own time without retrying it says "omp hasn't retried yet · N late" (never "Retrying…" for good), and "Paused · retries once you resume" while the conversation is frozen. Whether it still waits is read from omp's registry (`get_subagents`, `progress.retryState`).
- omp has no command that retries one subagent (`abort_retry` and `/retry` are the main session's; a message steered at the subagent, or sent by its parent, is read when the wait ends), so a usage-limit wait, or any wait omp is late on, offers **Stop and continue** — not a backoff of seconds, and never while the conversation is paused, whether the countdown still runs or its time is over, because the main agent that has to bring the subagent back is frozen too. It sends `cancel_subagent`, which ends the wait and parks the subagent with its transcript, then a message to the main agent asking it to bring the subagent back with `write` to the subagent's address: omp revives it from its transcript and it retries at once. Both go out as your own act, as Stop does.
- The subagent's name is a model's choice (`fix src/main.ts` is an ordinary one, and a name can be an instruction), so the message never has it as words: it carries only the percent-encoded address (`agent://fix%20src%2Fmain.ts`) to copy as it stands, which omp reads back to the same subagent. If the message is refused after the Stop, the toast says the subagent stays stopped until the main agent continues it. It is offered for a subagent the main agent started, not one another subagent started (that one says why it cannot be offered, and *Stop* ends it); the message is in the conversation like any you send and takes a turn of the main agent; *Stop* alone ends the subagent. `tests/contract/subagent-revive.test.ts` runs the whole sequence against the real omp, for a 402 and a 429 (with `retry-after` and with `retry-after-ms`) and for names with a space, a slash, a `%` and a `#`, other scripts, and an instruction.

### Two pages, one app (#587)

- What omp says once and does not repeat, the server keeps and hands to every page that attaches. A `!command` that is running appears with its *Stop* button on every page that has the conversation open (the server announces it with `bash_started` and `bash_ended`, and a page that attached after it began is told in `attached.held`); a compaction that is in progress, and the status lines and widgets an extension set (`setStatus`, `setWidget`), are on a late page as they are on the page that was there. The time worked on a turn that began before the page opened starts from the turn's own start (`LiveInfo.turnStartedAt`), not from the moment the page loaded. Archiving a conversation and marking a model as loved are the same on every page at once (`sessions_changed`, `favorite_models`).
- A draft in the composer stays on the page it is typed on, by decision, and so do the lines a page puts between messages as it hears them (a rule applied, a model fallback, what a command printed): a page that opens later shows what the transcript holds. A two-page harness (the app's local page and a page through the access tunnel stand-in, `tests/e2e/live-sync*.spec.ts`) drives each way: a conversation started on one page in the other's list, running, with its dot; streaming text and thinking; tool cards that open, stream and fold; a subagent's list, its full screen and a window opened on it; a dialog of every kind answered on one page and gone from the other; a message or a steer sent from either page queued in both queues without ending the turn; permission mode, model, preset, thinking level, goal, todos, session settings, the turn's clock and what it cost; Stop, pause and resume; a usage-limit wait and Retry now; a compaction, a `!command` and a status line set by an extension on a page that opens the conversation afterwards; a rename, an archive and a loved model. This does not let any page do more than before: a page that is not on this Mac still cannot change remote access settings or the guard, run the update or the migration, or open or reveal a file in the Finder.

### Network (#624)

- A server bound to a network address also listens on `127.0.0.1`, so its owner has a page on this computer: the loopback listener takes the same port when it is free there, and when another program holds it there, the next free one above it (up to 20 above), then any free one, and the banner says which and why. The startup banner prints both pages and which is the local one: `omp-webui also listening on http://127.0.0.1:7878: the page on this computer …`, then `Open: http://127.0.0.1:7878/?token=…  (this computer)` and the network's own. Which page is this computer's is still decided by the connection alone, never by which listener it came in on: a page on `http://192.168.1.5:7878` (a browser on this Mac too) is a remote page and is refused the guard, the tunnel's settings, the updater, moving to another computer, Open/Reveal and the projects folder with `403`; the macOS app is told the loopback port as the server's, and `server.pid` records it so that another server's guard asks about it too.
- A `0.0.0.0` or `::` bind is unchanged (one listener that already has the page at `127.0.0.1`); a server the macOS app started with a network host and no loopback listener fails to start and says why, since the app opens `127.0.0.1` and would find nothing there. `tests/contract/lan-bound.test.ts` runs the loopback page and what it may do, the network's refusals, the banner, a port that is taken, and checks over the socket that a page that is not this computer's is told nothing of the guard's settings or the app's updates.

### Safety and moving computers

- The guard's settings travel with Move to another computer: `guard.json` is part of *This app's data* in the archive's table, and while an import writes, the server's once-a-second look leaves `guard.json`, `approval.json` and the records of the conversations it keeps paused alone, however long the import takes; when the import ends the server takes the file the import wrote as its own, tells every gate and every page, and writes the kept conversations' records again.
- A release waits for a quiet Mac before it runs its suites, because the timing-sensitive tests flake when something else is using the machine: the 1-minute load average at or below `--max-load` (default half of this Mac's cores), read every 30 s for at most `--max-wait` minutes (default 20), each wait printed. A machine that does not get that quiet does not stop the release: it says the load, warns that a test that fails on timing may fail only here, and runs the suites; `--no-wait` skips the wait.
- The guard treats the server's own network address as its API (#634, fixed): a server bound to one address of a network (`OMP_WEBUI_HOST=192.168.1.5`, or a name such as `mymac.local`) is the same gate whichever of its addresses a command names, so a model's `curl http://192.168.1.5:7878/api/remote` is put to the guard like `127.0.0.1`'s is. The server writes those addresses into `<overlay>.risk` (`hosts`, beside `ports`), and the classifier reads them as it reads the loopback spellings (brackets for an IPv6 address, a zone written `%25`, case folded) on the same port rule: another program's API on that address on another port, and another computer's, does not ask. A wildcard (`0.0.0.0`, `::`), a list or a path puts no host in the file, and then only the loopback spellings ask, as before.

### Performance

- Host load reads the machine every 2 s only while a page shows its graphs (the sidebar's popover, the Host tab); the sidebar's line alone watches at the background pace (10 s), which is no reason to read the machine every 2 s, and a hidden tab or a page with no connection asks for nothing. `OMP_WEBUI_HOST_LIVE_MS` and `OMP_WEBUI_HOST_BACKGROUND_MS` in the README say so.
- New chat's footer no longer jumps while its controls load: the row of pickers holds its height and its widths (a soft grey row, `h-8`, icon-wide inside a narrow footer) while the chunk is fetched, so the message box does not move when they arrive; the spec sweeps 600, 700, 920, 1020 and 1400 px in English and Chinese.

### Development (#603)

- `bun run app-shots <before> <after>` photographs the macOS app's pages and lays two releases side by side, and it needs no screen that is on and unlocked (it runs with the Mac locked). Each input is an installer (`.dmg`), an `omp-webui.app` or a release tag (whose installer is downloaded with `gh`); one input only takes the pictures. It never starts the app: each bundle's own server and web build run in a new temporary `HOME`, omp agent directory, data directory and port with the test fixtures, theme and language are set through `POST /api/prefs`, and `tests/support/swift/appshots-harness.swift` (the app's own `WKWebView` configuration, the window never shown) takes the picture with `WKWebView.takeSnapshot` at 1280 × 840 points, 2×. The installed app and its preferences are not touched, disk images are mounted read-only and detached at the end, and an existing file is never replaced. Pictures go to `<out>/<version>/`, side by side into `compare/`, and the share of pixels that differ into `index.md`. The README's release checklist has the step.
- The dmg's layout waits for Finder to list the disk it just mounted before it lays the window out (up to 60 s), because Finder learns of a new disk a moment late and the first layout attempt used to fail with `Can't get disk "…" (-1728)` and only the retry passed.
- Two tests that failed only on a busy machine are now deterministic. The remote-window order test (`macos-remote.test.ts`, "WebKit's own callback order") made the page's second navigation with a 150 ms timer, which is a race twice over: under load the timer can fire before the request it interrupts has reached the server, which then records the opposite order, or after the harness's wait, which then reports a shorter list. The harness now runs the page's own `location = '/evil'` when WebKit reports that the first navigation has started, so the second follows the first by construction, and the order asserted is unchanged; each run has a 45 s bound that returns `timedOut` instead of a shorter list the test would read as the order, and the test's own timeout is above the sum of the three. And `security import` in the signing fixtures sometimes answers `CSSM_ModuleLoad()` while other suites are making their keychains on a busy machine, where the same import succeeds a moment later: `scripts/signing-identity.ts` now makes that import again, up to 5 times with a 100/200/300/400 ms backoff, and only on that error — a wrong passphrase or a missing keychain still fails at once. A fixture setup that throws also disposes what it made before the throw, so a throwaway keychain does not stay in the search list.

### Push notifications and home-screen app (#629)

- **A phone or a computer is told when a conversation finishes or needs you, with every page of it closed.** Settings › Notifications when this page is closed has *Notify this device* for this browser — a phone's Home Screen app, a computer's browser — and lists the devices the server notifies: each one's name, when it was last sent, a *Show a line of the message* switch (off by default), *Send a test* and *Revoke*, and *Revoke all devices* once there is more than one. Turning it on asks for the browser's permission from the click that turned it on (iOS refuses to ask otherwise), registers the service worker, subscribes against the server's key and tells the server, and it turns *Notifications* on, because the server pushes only while that setting is on (the page's own notifications and the macOS app follow the same switch). The card says why a browser cannot be told: the macOS app (it shows its own notifications), an address that is not secure (https, the tunnel's), a Safari tab on an iPhone or iPad (there only a Home Screen app has push, iOS 16.4 or later), or one with no service worker.
- **What is sent, and when.** The decision is the page's and the app's own, in one place that the tab title and the page's notifications use too (`shared/attention.ts`): a conversation that starts to wait for an answer is *asking*, one whose turn ends is *finished*, and an error or a usage limit ends a turn, so it is *finished* too. A message holds the conversation's saved title (120 characters; with none, the placeholder *Untitled session*, or *New conversation* before the conversation has a file — the first prompt is never used), the two words in the language you saved in Settings, else the device's own, and what a click opens (the conversation's file, else its process). A *preview*, for a device that switched one on, is the title of the dialog that waits or the last reply of the turn, one line of at most 120 characters taken from what the server holds anyway; nothing else of the conversation travels.
- **Encrypted for the one browser, and only to the browsers' own push services.** The message is `aes128gcm` (RFC 8291, padded to a multiple of 128 octets so its length says less of the title) and signed with this server's VAPID key (RFC 8292): the push service of Apple, Google, Mozilla or Microsoft carries it and cannot read it. A newer message about one conversation replaces an older one not yet delivered (`Topic`), an *asking* is `Urgency: high`, the service keeps a message for 6 hours, a push the service refuses is said once on the server's console and not retried, and 404 or 410 (the browser withdrew its subscription) takes the device off the list. Only those services are sent to, over https with no port written (443), and no redirect is followed, so a page that holds the token cannot make this Mac fetch an address of its own network; `OMP_WEBUI_PUSH_HOSTS` adds origins for a service of your own, and `OMP_WEBUI_PUSH_SUBJECT` names the contact a service may ask about this sender (`mailto:omp-webui@example.com` unless you set one, which Apple may refuse).
- **A device with a page on screen is not pushed to, and a page of a browser with push on stops posting its own notification.** The page says whether it is on screen over its socket (`{ "t": "presence", device, visible }`, again every 25 s; the server believes it for 70 s and forgets it when the socket closes), and the push is the notification where it is on. A device that subscribed through the tunnel is pushed to only while remote access is on, and pushes go out only while the server runs: a stopped server notifies nobody, and a message a service holds is delivered when the device is on. The macOS app's web view has no service workers and shows its own notifications, so the card is not for it.
- **What the server keeps.** `<data dir>/push-vapid.json` (the key pair, made on first use) and `<data dir>/push-devices.json` (each device's subscription, name, language and preview choice; at most 16 devices), both mode 0600, written whole and renamed into place. Neither is in a migration archive: a key must not travel and the subscriptions were made against it, so a new computer starts with no devices and each browser turns it on again. `GET /api/push` answers the public key and the devices and never an endpoint or a key; `POST /api/push/subscribe`, `/unsubscribe`, `/revoke`, `/revoke-all`, `/preview` and `/test` change them, a body over 8 KiB is refused by its `Content-Length` before it is read, and a test less than 5 seconds after another gets 429 with `Retry-After`. They are not local-only — a phone through the tunnel turns its own notifications on — and they need the token and the CSRF header like every route.
- **The page is installable.** `web/public/manifest.webmanifest` with its icons (and an `apple-touch-icon`) is what *Add to Home Screen* installs; it is linked with `crossorigin="use-credentials"` because a page behind Cloudflare Access gets it only with its cookie. The service worker (`web/public/sw.js`) does one thing, on purpose: it shows the notification and opens what a click names (`#/s/<file>`, else `#/live/<id>`), bringing a window of this app that is already open forward and telling it where to go. It has no `fetch` handler and no cache, so the page is never served from it and nothing a signed-in page was shown is kept in it; a payload it cannot read still shows a notification, because iOS and Chrome revoke a subscription that gets a push and shows nothing.
- **Tests.** `tests/unit/push-crypto.test.ts` (the message against RFC 8291's own example, the VAPID token), `push-devices.test.ts`, `push-hub.test.ts` (who is told, when, in what words, never twice) and `service-worker.test.ts` (what the worker may show, where a click goes) run without a browser or a server; `tests/contract/push.test.ts` runs the real server against a stand-in push service whose messages a stand-in browser decrypts, and `tests/e2e/push-settings.spec.ts` drives the card in a real browser. No test reaches a real push service.

### Machine switcher (#628)

- The sidebar has one more row once a Mac is saved: above Online / Offline, *This Mac ▾* (`h-8`). Its menu lists this Mac (connected or not, with a dot) and each saved Mac with when it was last opened, then *Add Mac…* — on this computer only, since only a page on this computer may change the list. It says which computer the conversations below belong to; it is not a third segment of Online / Offline, which still decides where this Mac's own new omp processes get their models. A computer with no saved Mac has no row, a remote window's page never shows it (`ompwWindow` without `ompwMacs`), and the menu and the dialog are a chunk of their own fetched the first time a Mac is saved, while the row's height is held so the list below it does not move.
- Choosing a Mac opens that Mac's page: in the macOS app (14 or later) in its own labelled window, through the `ompwMacs` bridge — the page posts `{ "type": "open", "id" }`, or `{ "type": "add" }` for the app's own sheet, and never names an address to the shell — and anywhere else (a browser, a phone, the app before macOS 14) in a new tab on `https://<host>/`, opened straight from the click so no popup blocker takes it, with `noopener,noreferrer`. *Add Mac…* in a browser asks for a name and an address and says which rule of the list a value breaks: at most 10 Macs, a name of at most 60 characters, and an address that is a public DNS host name — no port, user name or path, no IP address in any spelling, no `localhost` or `*.local`/`*.lan` and the like, no trailing dot, ASCII or its `xn--` form, and not `*.cloudflareaccess.com`.
- **One Mac list for the app and the pages.** The list is the server's file, `<data dir>/remote-macs.json` (mode 0600, written whole into a file of its own and renamed into place), so the app's **Macs** menu, a browser on this Mac and the app's own window show the same Macs; a file an earlier version of the app wrote is read as it is, so the Macs saved with the app are this list from the first start. The server is the only writer: the page reads it in `/api/meta` and is told of every change (`macs_changed`), the app reads the file again only when its size, date or inode changed (so the menu is there while the server is still starting) and asks the server for every change over `/api/macs` (`POST` to add, `…/<id>/rename`, `DELETE …/<id>`, `…/<id>/connected`, `…/<id>/team`). A page that is not on this computer reads the list in `/api/meta`, and every `/api/macs` route is refused to it with `403`. There is no token or cookie in the file, and it is machine state for *Move to another computer*: its `storeId`s name this computer's own WebKit stores, so it is left out of an archive.
- **One wildcard Access application serves several Macs, with one sign-in.** An Access application may have a wildcard domain (`*.example.com`): give each Mac a host name under it and the same team, AUD tag and addresses in Settings › Remote access there, and one sign-in covers all of them, because the token carries the one AUD tag each Mac's server checks. The card's guide, the *Check the address* message for an application that does not cover the host name, and the AI help's guide now say a wildcard that covers it does.
- **Export and import of what a second Mac needs.** Under the form, *Share these settings with another Mac* has *Export settings*, which saves `omp-webui-remote-access.json` (`{ "kind": "omp-webui-remote-access", "version": 1, "team", "aud", "emails" }`: the team, the AUD tag and the allowed addresses and nothing else — no host name, no tunnel, no credential, made from what the server has saved rather than from a half-typed form), and *Import settings…*, which reads such a file on another Mac and puts what it holds into the card's form. It fills only what the file has (a host name typed there stays), saves nothing (you check the fields and press Save), and says why it refused a file that is over 64 KiB, is not JSON, is not this app's, is of a version it cannot read, has nothing to apply, lists over 200 addresses, or holds settings the server would refuse.
- **A change in behaviour.** The Macs of one Cloudflare team now share one web data store, where each Mac used to have a store to itself. A remote window's web view takes a `WKWebsiteDataStore` for each Cloudflare team, shared by the Macs of that team so that one Access sign-in covers them all (its identifier is made from the team's name, so it is the same on every launch and no file keeps it); a Mac whose team is not known yet has a store of its own until the first sign-in pins it, and a window that is already open keeps the store it started with rather than dropping the sign-in under the page — the next window of that Mac uses the team's. The Macs of one team are therefore not walled off from each other the way a store each would have kept them: a page of one, if that Mac were compromised, can set a cookie for the parent domain they share, which can confuse or break another's sign-in. It cannot read their data: the access-token cookie is `HttpOnly` and belongs to its host alone, page storage is per origin, and a Mac's server refuses a request another site's page makes. So put under one team only Macs you trust alike.
- **Forgetting a Mac clears its origin data.** *Forget* takes the Mac out of the list (the server does, and while it cannot nothing is changed and nothing is closed), closes its windows and deletes the data stores no other Mac uses. A team's store another Mac still uses stays, and what the forgotten Mac put in it is deleted: its cookies by host (`omp.example.com` and `.omp.example.com`; a cookie for the parent domain stays, the others may use it, and so does the team's own `cloudflareaccess.com` sign-in, which is another site's) and the page-storage records no other Mac of that store shares (WebKit names a record by registrable domain, so `a.example.com`'s storage cannot be cut from `b.example.com`'s while both are listed: it goes with the last of them). Adding the Mac again therefore does not find it signed in.
- **One name for the app and the server.** The rules for a name and an address are the app's, written again in `shared/macs.ts` for the server, and the app's list and the server's cannot disagree about one: `tests/support/mac-vectors.ts` holds both to the same cases. Two names are one name when their folds are equal — NFKD, the marks dropped, lower case, upper case and lower case again, a final sigma `ς` read as `σ` (JavaScript reads a sigma by its place in a word and Swift does not, so neither decides), NFC — so `Straße` and `Strasse`, `ς` and `σ`, `ẞ` and `ss`, `Ǆ` and `dž` are each one name.
- What a Mac is doing (running, needs you) is not known yet: the per-Mac stream that will say it is not part of this step, so a saved Mac's dot is neutral and its line says only when the app last opened it, and this Mac's own dot is the page's connection. `tests/unit/macs.test.ts` and `saved-macs.test.ts` hold the rules and the file, `tests/contract/macs.test.ts` the routes and their refusals, `tests/unit/macos-remote.test.ts` the app's reading of the file and the store rules, and `tests/e2e/machine-switcher.spec.ts` the row and its menu.

### File transfer between Macs (#614)

- **New: files move between a page that is not on this computer — a browser through the tunnel, a phone, or the macOS app's window onto another Mac — and the folder a conversation works in.** The *Files* tab has a **Transfer** button (and a **Download** button on a file's preview): a file is saved with its own bytes, a folder is downloaded as a ZIP after the panel says what it will hold and what was left out and why, and what the tree hides (`dist`, `node_modules`, a dotfile) can be downloaded by path. Files and folders are uploaded with the two pickers or by dropping them on the tab or on a folder row, into the folder picked in the tree (the conversation's own folder when none is), in pieces of 8 MiB with a progress bar, *Cancel* and a retry of a piece that failed. The app's window onto another Mac saves a download through the system's save panel (an answer that says `attachment` is saved whatever its type, never shown in the window) and sends files through its open panel, which says which Mac they go to. The code of the feature is not in the first page (first-load JS stays at 201.7 KiB gzip).
- **A change in behaviour: uploads are on by default.** Settings › Remote access › **File transfer** is *Off*, *Download only* or *Download and upload*, and *Download and upload* is what a Mac that never chose gets. It is set on this computer only, read again at every request, and it applies to every page that is not on this computer, the composer's own file upload included (refused with `403` and the code `off` unless it is *Download and upload*); a page on this computer always has both. A settings file that cannot be read means *Off*.
- **Never overwritten unless the person picks Replace for the exact file they saw; never outside the folder.** An upload creates files: a name that is taken is asked about once for all the files of that upload (*Keep both* saves `name (1).ext` beside it and leaves the file that was there alone; *Replace* puts the new file in place of the one the page saw, and only that one — a plain, non-executable file that is still unchanged, otherwise it is refused; *Skip*), the bytes go to a hidden staged file and are published whole, and nothing is deleted, moved or made executable. The log names a file kept beside another by the name it was saved as and marks a replaced one (`"replaced": true`). Everything is confined to the conversation's folder: a path with `..`, an absolute path or a link that leads out is refused, and so are the home folder, this app's own data, protected places (`.ssh`, `.aws`, `.omp`, launch agents…, and for an upload also `.github/workflows` and `.github/actions`, which CI runs on a push), names that are hidden by default and secrets. Files begun together are counted against the limits at once, and the disk check takes off what the uploads going on have still to write. A download is always an attachment with `Content-Security-Policy: sandbox`, so a file is saved and never shown as a page of this server.
- **What a page that is not this computer's is given.** What the Files tab shows and, by decision, dotfiles and dependency and build folders — except when the conversation's folder is the home folder. Secrets (by name, or a private key by its content) and protected places are refused whatever they are called, and a ZIP leaves out secrets, links, sockets and devices, and hidden things below the folder unless asked for.
- **Content-Length.** A download sends `Content-Length` when the size is known (a `HEAD` always does) and never asserts it for a body that is streamed in pieces: chunked and a length never go together, and Bun leaves the header out of a streamed `GET`, so a client reads the size from a `HEAD`, a ZIP's plan or `Content-Range`.
- **The record.** Every download, ZIP and upload is a line in `<data dir>/transfers.jsonl` (mode 0600, rotated at 8 MiB): who (the Access email, `net:<address>`, or `local`), what, how big, the SHA-256 of an upload, and how it ended; never a query string, a token or file content. A line that cannot be written is said once and never fails the transfer. The README's *Remote access: moving files* has the rules, the limits and the codes; `tests/contract/folder-transfer.test.ts` runs them against the real server as the three kinds of page.

### Fixes found while releasing

- **An import no longer freezes the server on a file that is not a regular file.** Before it replaces a file, an import copies it into its backup; a named pipe in the data folder (where a list such as `favorite-models.json` belongs) was opened for that copy, synchronously, and the whole server stopped answering until something wrote to the pipe. The backup now copies only regular files and links (a pipe, a device or a socket has no contents to keep, and a restore passes over it), and a list preference that is not a regular file is an error that is never opened.
- **An import says it is done last.** Its state turned to *done* before the server had read again what it replaced and before conversations could open, so a page that opened one at once could be told an import was still writing. *Done* now comes after both.
- **On a phone, the conversation keeps following its end when you send.** While a send is in flight the line under the message box is one line instead of two, the browser cuts the scroll back by that much, and the page took the cut-back for you scrolling up and stopped following the reply. The page now records its place while the layout is still the short-lived one.

### 在后台运行（#627）

- **行为变化。** “在后台运行”现在让应用完全没有窗口（`macos/background.swift`、`macos/mainwindow.swift`、`macos/main.swift` 里的 `runInBackground`），而以前会留一个透明的窗口排在屏幕上。窗口被关闭，里面的页面也被释放——`WKWebView` 和它的网页进程一起消失，所以窗口不在调度中心、⌘-Tab 或 `⌘\`` 里，关闭别的应用的最后一个窗口也不会再把它带回来。应用不再是普通应用（`NSApp.setActivationPolicy(.accessory)`）：没有程序坞图标，系统也从不把它变成活动应用。服务器、所有对话（工作中的、已暂停的、在等待的）和远程访问（隧道）都继续；应用持有一个活动断言，让 macOS 不让它休眠（Mac 本身仍可睡眠）。子代理的弹出窗口和其他 Mac 的窗口会关掉；在原生全屏的窗口先退出全屏（最多 3 秒），最小化的窗口直接关闭；这期间再点一次“在后台运行”不起作用，而在应用等待页面时重新打开窗口会取消这次等待。
- **应用剩下的是菜单栏里的图标**：一个 `NSStatusItem`，用模板图，由菜单栏自己配色；有对话在等你的回答时旁边显示它们的数量。它的菜单有“打开 omp-webui”、一行说明有几个对话正在工作、几个需要你的输入（由服务器计数；在等待的对话不会同时算作正在工作），以及“退出 omp-webui”——那就是应用的退出：和 ⌘Q 同一个问题（退出 / 取消；有东西在工作时是“取消 / 仍然退出”；什么都不会被停止或留下时不问），点“取消”会让应用留在后台并把屏幕还回去。窗口会带着程序坞图标和一个全新的页面回来：从“打开”、从点击通知（页面打开在那个对话上）、或者再次打开这个应用（访达、启动台、它的第二份拷贝）；别的都不会把它带回来，包括激活这个应用。
- **没发送的草稿和所在的视图**能熬过窗口消失。页面把草稿镜像在会话存储里（`ompw.drafts`，随页面消失），打开的对话只在 `location.hash` 里；关窗前应用用脚本读出两者（最多等 1.5 秒；页面不回答就什么也不保留），在新页面的任何脚本运行之前把草稿放回它的会话存储（文档开始时的用户脚本，页面自己已经写过的地方不覆盖），并把视图接到地址后面，所以正在输入的消息、粘贴的图片和打开着的对话都还在。草稿**每个网页视图只放回一次**（`restoreDraftsScript` 先写下 `ompw.draftsRestored`）：没有这个标记，一次重新载入（⌘R、网页进程崩溃、服务器重启后的重新载入）会把已经发送过的草稿放回去。
- **终端继续运行。** 页面的 socket 一关，服务器就会结束它的终端，所以应用先告诉服务器这次关闭是有意的（`POST /api/shell/background`，只限本机，最多等 1.5 秒），服务器的 `PtyManager` 把接着关闭的那个页面的终端连同它们最后打印的内容（256 KiB；期间它们继续运行）留给重新打开的页面：终端页用 `pty_held` 询问，用 `pty_attach` 接管。没人接管的终端 24 小时或服务器结束时结束。这个通知被第一个留下终端的页面用掉，只有这台电脑上的页面才会留下终端，而且窗口在关闭之前或那 10 秒之内重新打开时它会被撤回（`DELETE`，和 POST 一样只限本机），所以这台电脑上的浏览器标签页此时关闭，不会被当成应用的窗口。
- **通知来自应用本身，而不是页面**（#627）：后台没有页面，页面就不能是听对话的那一方：由服务器决定什么值得通知，应用负责显示。`GET /api/shell/events`（`server/shell-events.ts`）是一个不结束的响应，内容是按行分隔的 JSON，应用从服务器起来那一刻起就读它（`macos/shellevents.swift`：带应用自己的令牌，连接断开或服务器重启后重新连接，每 15 秒一个空行，响应沉默了就能发现）。`{ "t": "state", "epoch", "working", "asking" }` 是菜单栏图标的计数，先发一次，之后任一变化时再发；`{ "t": "attention", "seq", "id", "kind", "title", "body", "liveId", "file" }` 是一个需要有人处理的对话：`asking`（有对话框在等：工具审批、提问）或 `finished`（这次运行结束了；对目标来说是整个运行）。规则就是页面原来的规则，现在集中在一处（`shared/attention.ts`，标签页标题和浏览器通知也用它），文字就是页面的文字，语言用保存的语言。错误或用量上限本身不单独通知：和以前一样，一轮结束，不管怎么结束，都是 `finished`。只在设置 › 通知开着时才有，而且这条路由只限本机，所以经隧道或经网络地址来的页面会被拒绝。**断了一段也不会丢通知**：应用读过之后，服务器保留最近 20 条通知并编号（`seq`，每次服务器运行从 1 开始，用 `epoch` 标明是哪一次运行），应用在卡顿之后、重新连接之后或被判定为落后而放开之后，会要它错过的那部分。应用用 `UNUserNotificationCenter` 显示横幅（每个对话一条，新的替换旧的），条件是 macOS 允许通知且没人在看窗口；点它会打开窗口并显示那个对话。页面完全不再在应用里弹通知（`shellShow` 和 `parked` 事件都去掉了）；浏览器里的页面不变。
- **标题由服务器来起**（`server/auto-title.ts`）：对话第一次交换之后用一次 `/rename`，不管有没有页面开着它，所以没有窗口时结束的对话也一样有名字（标题模型什么都不给时会再问两次，另一轮结束时再问一次）。设置里可以关掉，`OMP_WEBUI_AUTO_TITLE=off` 也可以。
- **看守的问题仍然能找到你。** 对话没有页面开着时，只要应用在后台运行并开着通知，“看守危险命令”（联系不上审核模型、并且开着“问我”）仍然会问人（`GuardHooks.reachable`）：这次调用等着，应用显示“需要你的输入”，菜单栏也计数，通知打开的窗口里就是那个问题。既没有页面也没有应用时，调用仍然和以前一样因为找不到审核模型而被拒绝。关闭窗口会和关闭浏览器标签页一样释放空闲对话：空闲回收会结束已经空闲 15 分钟的 omp，而正在工作、在等回答或已暂停的对话永远不会被回收。

### 变更（#630）

- “文件”标签页里有一个开关，**文件 | 变更**——是标签页里的开关，不是单独的标签页；它的代码在你第一次选它时才加载，在这之前不会向服务器要任何东西。变更**按设计只读**：它显示对话所在的文件夹和仓库最近一次提交相比有什么不同，不提供暂存、提交、恢复或丢弃。
- “工作区”列出每个有变更的文件，带分支、状态（已修改、新增、已删除、已重命名、类型变化、未跟踪、冲突）、是否有一部分已暂存，以及增加和删除的行数（二进制文件、特别大的文件和未跟踪文件没有行数）；点一个文件就打开它的变更，用**统一**方式显示（旧、新两列行号，带符号和底色，不只靠颜色），面板至少 520 px 宽时也可以**并排**显示，并按文件的语言着色，这个选择对所有文件都有效。“按轮次”按对话的每一轮列出 omp 的 `edit` 和 `write` 改过的文件（失败的调用没有改任何东西），最新的一轮在前，每个文件都链接到它的变更，文件已经和最近一次提交一致时会说明；`bash` 之类的命令改过的内容在“工作区”列表里。
- 新文件显示为全部新增；图片、二进制文件、git 不按文本比较的文件（超过 1 MiB）和链接只会说明原因而不画行，链接绝不会被跟随。限制：最多列出 500 个文件，一个变更最多 5000 行、每行 4000 个字符（被截断时页面会说明；很长的变更先画前 400 行，其余用按钮展开）。
- **运行的内容**：只有服务器上对对话所在文件夹运行的 `git status` 和 `git diff`，不带钩子、不带文件系统监视程序、不用外部比较程序、不做文本转换、不用分页器、不提示输入、不从远端获取；页面只说出对话和一个路径，别的什么都不说，所以列表里没有的路径找不到。仓库自己的设置指定了要让 git 运行的程序、把工作区放在了别处（`core.worktree`）、或者它的顶层不是这个文件夹或它的上一级时，不读取它，视图会说明；git 自己报错的仓库会显示为**无法读取**，这和“不是仓库”不是一回事。git 的输出列表读到 4 MiB、单个文件读到 2 MiB：超过就停掉 git，显示已读到的部分并标明被截断。文件夹里嵌套的仓库算一个条目，末尾带斜杠。不是这台电脑上的页面：默认隐藏和看起来像机密的文件既不显示也不报名字（只说数量），包含着私钥的变更会被拒绝，和“文件”标签页一样。

### 旁问（#633）

- **行为变化。** 旁问（侧边面板的“提问”标签页，omp 的 `/btw`）可以由你选的模型回答，而这样回答时，就不再是 omp 自己的回答。选择在问题框上方，整个应用只有一个，不是每个对话一个：和其他偏好一起保存（`ompw.btwModel`），在每个打开的页面里实时显示。默认是“omp 默认”，交给 omp：由对话自己的模型回答，和 `/btw` 完全一样。任何已连接的页面（远程页面也一样）都能改这个选择（它和主题一样是整个应用的偏好）。
- omp 的 `btw` 不能指定模型（它用会话的模型），而在提问前后改对话的模型会改变对话本身——它的记录和下一轮——所以选了别的模型时，由服务器用一个**单独的 omp 进程**回答：把对话的会话文件在这一刻的内容复制到数据目录里的私有文件夹（`btw-fork/`，文件夹 0700、文件 0600），在对话所在的文件夹里用对话自己的命令行、同样的 `--config` 覆盖和同样的闸门启动 `omp --mode rpc --resume <副本> --model <所选模型>`，发给它 `btw`，把回答流式写进同一个列表，然后结束进程；进程结束后副本就被删除，被强行结束的服务器留下的副本在下次启动时删除。对话、它的模型和它的文件都不会被碰，主智能体的下一轮仍然用对话自己的模型。每个回答都会写明“回答的模型：…”。离线模式：只能选对话所用后端的模型；选别的会由对话自己的模型回答，面板会说明。
- **和 omp 自己回答的区别**：它看到的是对话已保存的内容，所以看不到还在输出的那一轮（omp 自己回答时能看到），还没有文件的对话（刚开始、还没发第一条消息的新对话）则在没有上下文的情况下回答；需要启动一个进程（omp 和它的 MCP 服务器）；一个对话同一时间只运行一个这样的问题，下一个排队等候（一个对话最多保留两个在等的，第三个会被拒绝并给出提示；所有对话加起来最多同时运行三个，其余的等待空位）；追问沿用该话题开始时的模型，omp 自己回答过的话题的追问仍由 omp 回答；这些回答由服务器在运行期间保存（每个对话 30 条、最多 30 个对话），不在 omp 自己的旁问历史里，TUI 的 `/btw` 看不到它们。omp 还会把它打开的每个会话文件登记在 `<agent dir>/custom-session-files/`，所以每个这样的问题会在那里留下两个很小的标记（它们指向的文件消失后，omp 的 `gc --stale` 会清掉）。因为对话已保存的全部内容会发给所选模型的提供商，README 在讲这个选择的地方写明了这一点；兼容表也记下了 omp 的 `btw` 不能指定模型，以及改用的是什么。

### 导出（#632）

- **行为变化。** 导出现在是一个选择：导出卡片里，表格中每一类数据（对话、提示词历史、记忆、设置、自定义内容、插件、这个应用的数据）各有一个复选框，旁边是文件数和大小，一开始全部勾选；合计、以及“配置文件里留空的密钥值”的提示，都只算勾选的内容。**登录信息**不是复选框，它仍是下面那个要密码的开关，默认关闭、保持原来的警告。什么都没勾选又没有包含登录信息时，**导出**不可点，并说明原因。
- 服务器只导出所选的类别：请求里的 `categories` 是数据类别的 id 列表（不写就是全部七类）；写了 `credentials`、写了不存在的类别、或者不是列表，会在开始之前就得到 400（`migrateCategories`），什么都没选得到 400（`migrateNothingChosen`）。名字上就是密钥的文件（`.env`、密钥）跟着它所在文件夹的类别走，所以只勾选“设置”并包含登录信息时，技能文件夹里的 `.env` 不会进文件。
- 清单（`manifest.json`）记录这个文件包含哪些类别（`categories`；有加密的登录信息部分时才含 `credentials`），完成后的导出也会写出来；只勾选“记忆”而对话和提示词历史不在文件里时，还会记下记忆库所用文件夹的路径（`bankFolders`，只含和记忆库名字对得上的）。导入时，预览只列出文件里有的类别，并说明这台 Mac 上其余的一切原样不动；导入只写清单里的条目，加密部分的文件也只写到文件包含的类别所在的地方（名字上就是密钥的文件还需要它所在文件夹的类别），所以其他每个类别都逐字节保持原样——只有在要写 omp 的文件时才关闭空闲的对话进程。路径落在清单没有列出的类别里的条目会让文件成为损坏的文件，什么都不会写；清单里没有类别记录的文件（这个版本之前做的）算整份导出，和以前一样导入。
- 只选一部分时要知道的：这个应用的数据里的那些列表（已归档、权限选择、置顶）用对话的文件名来指对话，所以不包含“对话”时，它们指的是这台 Mac 上没有的文件；不包含“对话”时，`session-roots.json` 里的 `--session-dir` 文件夹也不会搬到这个应用自己的文件夹，只是把它们的旧主目录换成这台 Mac 的。

### 预设（#631）

- 设置 › 预设里每个全局预设都有“编辑”按钮。在同一个对话框里改它每个角色的模型、默认思考强度（也可以不设置）和子代理模型，点一次保存就通过 `omp config set modelPresets` 一次写入该预设的条目：条目里其他键（包括 omp 或这里不认识的）原样保留，编辑预设不会应用它。项目配置定义的预设仍然只读，服务器也会拒绝。
- 当前生效的预设排在列表最前面并标出：设置页按全局配置判断，输入框的预设菜单按该对话判断；其余预设保持原有顺序。“生效”仍只由角色和思考强度决定，对话选中的预设只用来在匹配的预设之间取舍，所以不匹配的预设永远不会显示为生效。对话框随设置页懒加载，不进首屏。
- 输入框的预设菜单现在会给带着子代理模型的预设加一个图标，悬停提示里列出这些模型，所以同时设置了 `task.agentModelOverrides` 的预设在应用之前就能分辨出来——屏幕阅读器也读得到（英文和中文都有）。

### 子代理（#594）

- 等待重试的子代理在“子代理”标签页里显示 omp 重试的时间和倒计时；omp 超过自己的时间 30 秒仍没有重试时，显示“omp 还没有重试 · 已晚 N”（不再永远写“正在重试…”），对话被冻结时显示“对话已暂停 · 恢复后重试”。它是否还在等待，以 omp 的注册表（`get_subagents`、`progress.retryState`）为准。
- omp 没有“立即重试某个子代理”的命令（`abort_retry` 和 `/retry` 是主会话的；发给子代理的消息，或它的父代理发的消息，都要等待结束后才会被读到），所以用量上限的等待，或 omp 已经晚了的等待，会提供**“停止并继续”**——秒级的退避不提供；对话暂停时一律不提供，不论倒计时还在走还是已到点，因为要把子代理接回来的主代理也被冻结了。它先发送 `cancel_subagent`，结束等待并把子代理连同记录一起停放，再给主代理发一条消息，请它对子代理的地址用 `write` 把子代理接回来：omp 从它的记录里把它复活，它立即重试。两步都以你自己的操作发出，和“停止”一样。
- 子代理的名字是模型起的（`fix src/main.ts` 很平常，名字也可能是一句指令），所以消息里从不把它当文字写出来，只带百分号编码后的地址（`agent://fix%20src%2Fmain.ts`），请主代理原样照抄，omp 会把它还原成同一个子代理。停止之后这条消息若被拒绝，提示会说明子代理会一直停着，直到主代理继续它。它只适用于主代理直接启动的子代理，另一个子代理启动的那种会说明为什么不能提供（“停止”可以结束它）；这条消息和你发的其他消息一样在对话里，会占用主代理的一轮；“停止”单独就结束这个子代理。`tests/contract/subagent-revive.test.ts` 用真实的 omp 跑完整个流程，覆盖 402 和 429（带 `retry-after` 和带 `retry-after-ms`），以及名字里有空格、斜杠、`%`、`#`、其他文字和一句指令的情况。

### 两个页面，一个应用（#587）

- omp 只说一次、不会重复的内容，由服务器记下来，交给每个连上的页面。正在运行的 `!命令` 连同它的“停止”按钮出现在每个打开这个对话的页面上（服务器用 `bash_started` 和 `bash_ended` 帧告知，开始之后才连上的页面在 `attached.held` 里被告知）；正在进行的压缩，以及扩展设置的状态行和小组件（`setStatus`、`setWidget`），晚到的页面上和先到的页面上一样。页面打开之前就已开始的一轮，工作时间从这一轮自己的开始时刻算起（`LiveInfo.turnStartedAt`），不是从页面加载的那一刻。归档对话和收藏模型，在每个页面上同时一样（`sessions_changed`、`favorite_models`）。
- 输入框里的草稿留在输入它的页面上，这是有意的；页面在消息之间听到时加上的那些行（应用了的规则、模型回退、命令打印的内容）也一样：晚打开的页面显示对话记录里有的。一个双页面的测试装置（应用本机的页面，加上一个经隧道替身进来的页面，`tests/e2e/live-sync*.spec.ts`）双向驱动这些：一个页面开始的对话出现在另一个页面的列表里、正在运行、带圆点；流式文字和思考；打开、流式输出并收起的工具卡片；子代理的列表、它的全屏页面和一个在它上面打开的窗口；每种对话框都在一边显示、在另一边回答之后从这里消失；从任一页面发出的消息或引导进入两边的队列，且不结束这一轮；权限模式、模型、预设、思考强度、目标、待办、会话设置、这一轮的用时和花费；停止、暂停和恢复；用量上限的等待和“立即重试”；一个页面之后才打开对话时，正在进行的压缩、正在运行的 `!命令` 和扩展设置的状态行；改名、归档和收藏的模型。这并没有让任何页面能做得比以前更多：不在这台 Mac 上的页面仍然不能改远程访问设置或看守、运行更新或迁移、在访达中打开或显示文件。

### 网络（#624）

- 绑定在网络地址上的服务器同时在 `127.0.0.1` 上监听，所以它的主人在这台电脑上也有页面：回环监听在端口空闲时用同一个端口；如果该端口在回环上被别的程序占用，就用它上面第一个空闲的端口（最多往上 20 个），再不行就用任意空闲端口，启动横幅会说明用了哪个、为什么。启动横幅会打印两个页面并说明哪个是本机的：`omp-webui also listening on http://127.0.0.1:7878: the page on this computer …`，然后是 `Open: http://127.0.0.1:7878/?token=…  (this computer)` 和网络那个。哪个页面是这台电脑的，仍然只由连接决定，而不是由它从哪个监听进来：在 `http://192.168.1.5:7878` 上打开的（在这台 Mac 上的浏览器也一样）是远程页面，看守、隧道设置、更新、迁移到另一台电脑、“打开”“在访达中显示”和项目文件夹都对它返回 `403`；macOS 应用被告知的是回环端口，因为那才是它连的地方，`server.pid` 也记下这个端口，让别的服务器的看守同样询问它。
- 绑定 `0.0.0.0` 或 `::` 时没有变化（本来就是一个监听、页面在 `127.0.0.1`）；macOS 应用用网络地址启动、却又拿不到回环监听时，服务器会启动失败并说明原因，因为应用打开的是 `127.0.0.1`，那里什么也不会有。`tests/contract/lan-bound.test.ts` 跑一遍回环页面和它能做的事、网络那边的拒绝、启动横幅、被占用的端口，并在 socket 上检查不是这台电脑的页面收不到看守设置和应用更新的任何消息。

### 安全与迁移

- 防护设置会随“迁移到另一台电脑”一起走：`guard.json` 属于归档表格里“这个应用的数据”这一类；导入写入期间，服务器每秒一次的那次检查不会碰 `guard.json`、`approval.json` 和它保留着的那些暂停对话的记录，不管导入要写多久；导入结束时，服务器把导入写下的文件当作自己的，告诉每个闸门和每个页面，并把保留对话的记录重新写一遍。
- 发布前会先等这台 Mac 闲下来，再跑测试，因为对时间敏感的测试在机器还在忙别的事时会偶发失败：判据是 1 分钟负载不超过 `--max-load`（默认是这台 Mac 核心数的一半），每 30 秒读一次，最多等 `--max-wait` 分钟（默认 20），每次等待都会打印出来。一直闲不下来也不会让发布停下：它报出当时的负载、提示“只有在时间上失败的测试可能只在这里失败”，然后照常跑测试；`--no-wait` 跳过这段等待。
- 看守把服务器自己的网络地址也当作它的 API（#634，已修复）：绑定在网络某个地址上的服务器（`OMP_WEBUI_HOST=192.168.1.5`，或者 `mymac.local` 这样的名字），不论命令写的是它的哪个地址，都是同一个检查点，所以模型命令里的 `curl http://192.168.1.5:7878/api/remote` 会和写 `127.0.0.1` 时一样被拿去询问。服务器把这些地址写进 `<overlay>.risk`（`hosts`，和 `ports` 并列），分类器像读回环的几种写法一样读它们（IPv6 地址加方括号、网卡区域写成 `%25`、大小写折叠），端口规则对两份列表也一样：只有端口是一个 omp-webui 可能服务的端口时 `/api/` 才询问，所以同一地址上另一个端口上别的程序的 API，以及别的电脑的 API，都不询问。通配地址（`0.0.0.0`、`::`）、列表或者路径不会往文件里写任何主机，那时仍然和以前一样只认回环的写法。

### 性能

- 只有页面在显示本机负载的曲线时（侧边栏的弹出面板、“本机”标签页），服务器才每 2 秒读一次机器；只有侧边栏那一行在显示时按后台的节奏（10 秒）读，那还不足以每 2 秒读一次机器；隐藏的标签页和没有连接的页面什么都不请求。README 里 `OMP_WEBUI_HOST_LIVE_MS` 和 `OMP_WEBUI_HOST_BACKGROUND_MS` 的说明就是这样写的。
- 新对话底部的控件加载时不再让输入框跳动：取回之前那一行（几个选择器）占住自己的高度和宽度（一条淡灰色的行，`h-8`，窄的输入框里是图标的宽度），所以它们到达时输入框不会移位；spec 在 600、700、920、1020 和 1400 px 宽度下，英文和中文各扫一遍。

### 开发（#603）

- `bun run app-shots <before> <after>` 给 macOS 应用的页面拍照，并把两个版本并排放在一起，而且**不需要屏幕亮着并解锁**（Mac 锁着也能跑）。每个输入是安装包（`.dmg`）、一个 `omp-webui.app` 或者一个发布标签（它的安装包由 `gh` 下载）；只给一个输入时只拍照。它从不启动应用：每个包自己的服务器和网页构建跑在新的临时 `HOME`、omp agent 目录、数据目录和端口里，配测试样例，主题和语言通过 `POST /api/prefs` 设置，再由 `tests/support/swift/appshots-harness.swift`（应用自己的 `WKWebView` 配置，窗口从不显示）用 `WKWebView.takeSnapshot` 在 1280 × 840 点、2× 下拍照。已安装的应用和它的偏好不会被碰，磁盘映像只读挂载并在结束时推出，已存在的文件绝不覆盖。图片写到 `<out>/<版本>/`，并排的放进 `compare/`，像素不同的比例写进 `index.md`。README 的发布清单里有这一步。
- dmg 的布局在动手之前先等 Finder 列出它刚挂载的磁盘（最多 60 秒），因为 Finder 要过一会儿才认新磁盘，而以前第一次布局会报 `Can't get disk "…" (-1728)`，只有重试才过。
- 两个只在机器忙时才失败的测试现在确定了。远程窗口的顺序测试（`macos-remote.test.ts` 里的“WebKit 自己的回调顺序”）让页面用 150 毫秒的定时器做第二次跳转，这是一处两重的竞态：负载高时定时器可能在被打断的请求到达服务器之前就触发，服务器于是记下相反的顺序；也可能在测试装置的等待之后才触发，于是只拿到一个更短的列表。现在测试装置在 WebKit 报告第一次跳转已经开始时，才让页面自己执行 `location = '/evil'`，所以第二次按构造跟在第一次之后，断言的顺序不变；每次运行有 45 秒的界限，到点返回 `timedOut`，而不是让测试把更短的列表当成顺序，测试自己的超时则高于三次运行之和。另外，签名装置里的 `security import` 在机器忙、别的套件正在建自己的钥匙串时，偶尔会报 `CSSM_ModuleLoad()`，而同样的导入过一会儿就成功：`scripts/signing-identity.ts` 现在会重做这次导入，最多 5 次，退避 100/200/300/400 毫秒，而且只对这种错误重做——密码错了或者钥匙串不存在仍然立刻失败。装置在建立过程中抛错时，也会把它此前建好的东西清理掉，所以一次性的钥匙串不会留在搜索列表里。

### 页面关闭时的通知与主屏幕应用（#629）

- **对话结束或需要你时，即使这个页面全都关着，手机或电脑也会收到通知。** 设置 ›“页面关闭时的通知”里有“通知这台设备”，用于这个浏览器——手机的主屏幕应用、电脑上的浏览器——并列出服务器会通知的设备：每个设备的名称、上次发送的时间、“显示一行消息内容”开关（默认关闭）、“发送测试”和“撤销”，有不止一台时还有“撤销所有设备”。开启时会从打开它的那次点击里请求浏览器的权限（否则 iOS 拒绝询问）、注册 service worker、用服务器的密钥订阅并告诉服务器，同时会打开“通知”，因为服务器只在这个设置打开时才推送（页面自己的通知和 macOS 应用跟随的是同一个开关）。浏览器不能收到通知时，卡片会说明原因：macOS 应用（它显示自己的通知）、不是安全地址（https，即隧道的地址）、iPhone 或 iPad 上的 Safari 标签页（那里只有主屏幕应用才有推送，需要 iOS 16.4 或更高），或者没有 service worker。
- **发什么，什么时候发。** 判断和页面、应用自己的判断一样，集中在一处（`shared/attention.ts`，标签页标题和页面自己的通知也用它）：开始等你回答的对话是“需要你的输入”，一轮结束的对话是“已完成”，出错或用量上限会结束一轮，所以也是“已完成”。消息里有对话已保存的标题（120 个字符；没有标题时是占位的“未命名对话”，对话还没有文件时是“新对话”——第一条提示词从不使用）、按你在设置里保存的语言写的两个词（没保存时用设备自己的语言），以及点一下要打开的东西（对话的文件，没有文件时是它的进程）。为开了“显示一行消息内容”的设备准备的**预览**，是在等你的那个对话框的标题，或者这一轮最后一条回复，一行、最多 120 个字符，取自服务器本来就持有的内容；对话的其他内容都不外发。
- **只为这一台浏览器加密，而且只发给浏览器厂商自己的推送服务。** 消息用 `aes128gcm`（RFC 8291，填充到 128 字节的整数倍，让长度也说不出多少标题内容），并用这个服务器自己的 VAPID 密钥签名（RFC 8292）：Apple、Google、Mozilla、Microsoft 的推送服务只负责转交，读不到内容。同一个对话的新消息会替换掉还没送出的旧消息（`Topic`），“需要你的输入”用 `Urgency: high`，服务最多保留 6 小时；服务拒绝的推送在服务器控制台上说一次，不重试；服务回答 404 或 410（浏览器已经退订）就把这台设备从列表里去掉。只发给这些服务，走 https 和它们自己的端口，不跟随重定向，所以拿着令牌的页面也没法让这台 Mac 去访问它自己网络里的地址；`OMP_WEBUI_PUSH_HOSTS` 可以为自己的推送服务加上来源，`OMP_WEBUI_PUSH_SUBJECT` 写明推送服务可以询问的发送者联系方式（不设时是 `mailto:omp-webui@example.com`，Apple 可能会拒绝它）。
- **设备有页面在屏幕上时不推送；开了推送的浏览器，页面也不再自己发通知。** 页面通过自己的 socket 说明是否在屏幕上（`{ "t": "presence", device, visible }`，每 25 秒再说一次；服务器相信 70 秒，socket 关闭时立刻忘掉），推送就是通知。经隧道订阅的设备，只在远程访问开着时才推送；而且只在服务器运行时才推送：服务器停着谁也不通知，服务替设备留着的消息在设备开机时送达。macOS 应用的网页视图没有 service worker，显示的是它自己的通知，所以这张卡片不是给它用的。
- **服务器保存的东西。** `<数据目录>/push-vapid.json`（密钥对，第一次使用时生成）和 `<数据目录>/push-devices.json`（每台设备的订阅、名称、语言和预览选择；最多 16 台），权限都是 0600，整体写入再移动到位。这两个文件都不进迁移归档：密钥不能跟着走，而订阅是针对它做的，所以新电脑一开始没有设备，每个浏览器要重新开启一次。`GET /api/push` 只回答公钥和设备列表，从不回答 endpoint 或密钥；`POST /api/push/subscribe`、`/unsubscribe`、`/revoke`、`/revoke-all`、`/preview` 和 `/test` 改变它们，正文超过 8 KiB 会在读取之前就按 `Content-Length` 拒绝，距离上一次测试不到 5 秒会得到带 `Retry-After` 的 429。它们不是只限本机的——经隧道进来的手机要给自己开通知——和别的路由一样需要令牌和 CSRF 头。
- **页面可以安装。** `web/public/manifest.webmanifest` 和它的图标（还有 `apple-touch-icon`）就是“添加到主屏幕”安装的东西；它用 `crossorigin="use-credentials"` 引入，因为 Cloudflare Access 后面的页面只有带上 cookie 才拿得到它。service worker（`web/public/sw.js`）按设计只做一件事：显示通知，并打开点击所指的东西（`#/s/<文件>`，否则 `#/live/<id>`），把这个应用已经打开的窗口带到前台并告诉它去哪里。它没有 `fetch` 处理也没有缓存，所以页面从不经由它提供，登录后的页面看到的内容也不会留在它那里；读不懂的内容仍然会显示一条通知，因为 iOS 和 Chrome 会撤销“收到推送却什么都不显示”的订阅。
- **测试。** `tests/unit/push-crypto.test.ts`（对照 RFC 8291 自带的例子检查消息，以及 VAPID 令牌）、`push-devices.test.ts`、`push-hub.test.ts`（通知谁、什么时候、用什么话、绝不重复）和 `service-worker.test.ts`（worker 能显示什么、点击去哪里）不需要浏览器或服务器；`tests/contract/push.test.ts` 用真实的服务器对着一个替身推送服务运行，消息由替身浏览器解密；`tests/e2e/push-settings.spec.ts` 在真实浏览器里驱动这张卡片。没有任何测试会连真实的推送服务。

### 机器切换（#628）

- 保存过 Mac 之后，侧边栏会多一行：在“在线 / 离线”上面，是“这台 Mac ▾”（`h-8`）。它的菜单列出这台 Mac（已连接或未连接，带圆点）和每台保存的 Mac 及上次打开它的时间，最后是“添加 Mac…”——只在运行服务器的这台电脑上可用，因为只有这台电脑上的页面能改这份列表。这一行说的是下面的对话属于哪台电脑，不是“在线 / 离线”的第三段——后者仍然决定这台 Mac 自己新起的 omp 进程从哪里取模型。没有保存任何 Mac 的电脑没有这一行；其他 Mac 窗口里的页面从不显示它（有 `ompwWindow` 而没有 `ompwMacs`）；菜单和对话框是独立的代码块，第一次保存 Mac 时才获取，而这期间那一行占住自己的高度，所以下面的列表不会移位。
- 选一台 Mac 就打开它的页面：在 macOS 应用里（14 或更高）打开它自己带标签的窗口，经由 `ompwMacs` 桥——页面发出 `{ "type": "open", "id" }`，或者对应用自己的表单发出 `{ "type": "add" }`，从不向应用说出地址；其他地方（浏览器、手机、macOS 14 之前的应用）在 `https://<主机名>/` 上开一个新标签页，直接从这个点击里开出，所以不会被弹窗拦截，并带 `noopener,noreferrer`。浏览器里的“添加 Mac…”要求名称和地址，并说明某个值违反了列表的哪条规则：最多 10 台 Mac，名称最多 60 个字符，地址必须是一个公网 DNS 主机名——不能带端口、用户名或路径，不能是任何写法的 IP 地址，不能是 `localhost` 或 `*.local`/`*.lan` 之类，不能以点结尾，非 ASCII 要写成 `xn--` 形式，也不能是 `*.cloudflareaccess.com`。
- **应用和页面共用一份 Mac 列表。** 列表是服务器上的文件 `<数据目录>/remote-macs.json`（权限 0600，整体写入到一个自己的文件再移动到位），所以应用的“Macs”菜单、这台 Mac 上的浏览器和应用自己的窗口看到的是同一批 Mac；应用早期版本写下的文件按原样读取，所以用应用保存过的 Mac 从这个版本第一次启动起就是这份列表。只有服务器写它：页面在 `/api/meta` 里读到它，并在每次变化时收到通知（`macs_changed`）；应用只在文件的大小、日期或 inode 变化时才重新读（所以服务器还在启动时菜单就已经在了），每次改动都通过 `/api/macs` 请服务器做（`POST` 添加、`…/<id>/rename`、`DELETE …/<id>`、`…/<id>/connected`、`…/<id>/team`）。不在这台电脑上的页面在 `/api/meta` 里读到这份列表，而 `/api/macs` 的每条路由都对它返回 `403`。文件里没有令牌也没有 cookie，而且它是“迁移到另一台电脑”时的机器状态：里面的 `storeId` 指的是这台电脑自己的 WebKit 存储，所以它不进归档。
- **一个通配符的 Access 应用服务多台 Mac，一次登录就够。** Access 应用可以用通配域名（`*.example.com`）：给每台 Mac 一个它下面的主机名，并在每台 Mac 的“设置 › 远程访问”里填同样的团队名、AUD 标签和邮箱地址，一次登录就够所有这些 Mac，因为令牌里带的是每台 Mac 的服务器都要核对的那一个 AUD 标签。卡片里的指引、“检查地址”在应用没有覆盖主机名时给出的说明、以及 AI 助手的指引，现在都写明覆盖该主机名的通配符也可以。
- **导出和导入第二台 Mac 需要的东西。** 表单下面是“把这些设置分享给另一台 Mac”，其中有“导出设置”，保存 `omp-webui-remote-access.json`（`{ "kind": "omp-webui-remote-access", "version": 1, "team", "aud", "emails" }`：团队名、AUD 标签和允许的邮箱地址，仅此而已——没有主机名、没有隧道、没有任何凭据，而且由服务器已保存的内容生成，不是由写到一半的表单生成）；还有“导入设置…”，在另一台 Mac 上读取这样的文件，把里面的内容填进那张卡片的表单。它只填文件里有的项（那里已经写好的主机名保留），什么也不保存（由你看过字段再点“保存”），并说明为什么拒绝一个文件：超过 64 KiB、不是 JSON、不是这个应用导出的、版本读不了、没有任何可应用的内容、列了超过 200 个邮箱地址，或者里面的设置服务器会拒绝。
- **行为变化。** 同一个 Cloudflare 团队的 Mac 现在共用一份网页数据存储，而以前每台 Mac 各有一份。远程窗口的网页视图按团队各取一份 `WKWebsiteDataStore`，由该团队的 Mac 共用，所以一次 Access 登录就够它们全部（它的标识符由团队名算出，每次启动都一样，没有文件保存它）；团队还不知道时，那台 Mac 有自己的存储，直到第一次登录把它定下来，而已经打开的窗口仍用它启动时的那份存储，不会在页面底下把登录状态换掉——那台 Mac 的下一个窗口才用团队的存储。因此同一个团队的 Mac 之间不再像每台各有一份存储那样互相隔开：其中一台的页面，如果那台 Mac 被攻破，可以为它们共有的上级域名设 cookie，从而搅乱或弄坏另一台的登录。但读不到它们的数据：访问令牌的 cookie 是 `HttpOnly` 的、只属于它自己的主机，页面存储按源隔离，而一台 Mac 的服务器会拒绝另一个网站的页面发来的请求。所以一个团队下只放同样信任的 Mac。
- **忘记一台 Mac 会清掉它的源数据。**“忘记”把 Mac 从列表里去掉（由服务器做，做不到时什么也不改、什么也不关），关掉它的窗口，并删掉没有别的 Mac 在用的存储。另一个 Mac 还在用的团队存储会留下，但那台被忘掉的 Mac 放进去的东西会被删掉：按主机删它的 cookie（`omp.example.com` 和 `.omp.example.com`；上级域名的 cookie 留着，别的 Mac 可能要用，团队自己的 `cloudflareaccess.com` 登录也留着，那是另一个网站的），以及这份存储里没有别的 Mac 共用的页面存储记录（WebKit 以可注册域名给记录命名，所以两台都列着时，`a.example.com` 的存储没法从 `b.example.com` 的里面切出来：它跟着最后那台一起走）。因此再次添加这台 Mac 时，它不会是已登录的状态。
- **应用和服务器用同一套名称规则。** 名称和地址的规则是应用的，`shared/macs.ts` 为服务器又写了一遍，应用的列表和服务器的列表不可能对同一项有不同看法：`tests/support/mac-vectors.ts` 把两边钉在同一批用例上。两个名字折叠后相同就是一个名字——NFKD、去掉记号、转小写、再转大写和小写、词尾的 `ς` 读作 `σ`（JavaScript 按词中的位置读 sigma，Swift 不这样读，所以两边都不作决定）、NFC——所以 `Straße` 和 `Strasse`、`ς` 和 `σ`、`ẞ` 和 `ss`、`Ǆ` 和 `dž` 各自是同一个名字。
- 一台 Mac 现在在做什么（运行中、需要处理）还不知道：会说这件事的每台 Mac 的事件流不在这一步里，所以保存的 Mac 圆点是中性的，那一行只说应用上次打开它的时间；这台 Mac 自己的圆点表示页面的连接。`tests/unit/macs.test.ts` 和 `saved-macs.test.ts` 管规则和文件，`tests/contract/macs.test.ts` 管路由和它们的拒绝，`tests/unit/macos-remote.test.ts` 管应用怎样读这个文件和存储规则，`tests/e2e/machine-switcher.spec.ts` 管这一行和它的菜单。

### Mac 之间的文件传输（#614）

- **新增：不在这台电脑上的页面——经隧道的浏览器、手机，或 macOS 应用里通向另一台 Mac 的窗口——可以和对话所在的文件夹之间传文件。** “文件”标签页有一个**传输**按钮（文件预览里还有一个**下载**按钮）：文件按它自己的字节保存；文件夹下载为 ZIP，面板会先说 ZIP 里有什么、漏掉了什么和为什么；树里隐藏的东西（`dist`、`node_modules`、点开头的文件）可以按路径下载。文件和文件夹可以用两个选择按钮上传，也可以拖到标签页上或某个文件夹行上，放进在树里选中的文件夹（没选时是对话自己的文件夹），每片 8 MiB，带进度条、“取消”，失败的一片会重试。通向另一台 Mac 的窗口通过系统的保存面板保存下载（写着 `attachment` 的回答不管是什么类型都被保存，从不在窗口里显示），用打开面板发送文件，面板会说明它们发往哪台 Mac。这个功能的代码不在首屏里（首屏 JS 保持 201.7 KiB gzip）。
- **行为变化：上传默认开启。** 设置 › 远程访问 ›**文件传输**有“关闭”“仅下载”“下载和上传”，从没选过的 Mac 得到的是“下载和上传”。它只能在这台电脑上设置，每个请求都重新读，适用于每个不在这台电脑上的页面，输入框自己的文件上传也在内（不是“下载和上传”时回答 `403`、代码 `off`）；这台电脑上的页面总是两者都有。读不了的设置文件按“关闭”处理。
- **从不覆盖，除非使用者对自己看到的那个确切文件选了“替换”；从不出文件夹。** 上传只创建文件：名字已被占用时，对这次上传的所有文件只问一次（“都保留”存成它旁边的 `名字 (1).扩展名`，原来的文件不动；“替换”让新文件取代页面看到的那个文件，也只取代它——必须是仍然没变的、普通的、不可执行的文件，否则被拒绝；“跳过”），字节先写进隐藏的暂存文件、最后整个发布，绝不删除、移动任何东西，也不把东西变成可执行。日志里，保留在另一个文件旁边的文件记在它存成的名字下，被替换的有标记（`"replaced": true`）。一切都限制在对话的文件夹里：带 `..` 的路径、绝对路径和通向外面的链接都会被拒绝，家目录、这个应用自己的数据、受保护的地方（`.ssh`、`.aws`、`.omp`、启动代理……；对上传来说还有 CI 在推送时运行的 `.github/workflows` 和 `.github/actions`）、默认隐藏的名字和机密也一样。一起开始的文件会立刻计入限制，磁盘检查也会减去正在进行的上传还要写入的字节。下载总是带 `Content-Security-Policy: sandbox` 的附件，所以文件只会被保存，不会被当作这个服务器的页面显示。
- **不在这台电脑上的页面能得到什么。** 文件页签显示的东西，加上（按使用者的决定）点开头的文件以及依赖和构建文件夹——对话的文件夹是家目录时例外。机密（按名字，或按内容识别出的私钥）和受保护的地方不管叫什么都拒绝；ZIP 会漏掉机密、链接、套接字和设备，以及文件夹里面的隐藏内容（除非要求包含）。
- **Content-Length。** 下载在大小已知时发送 `Content-Length`（`HEAD` 总是带），而对分片流式发出的正文从不保证它：分块和长度从不同时出现，Bun 会把流式 `GET` 的这个头去掉，所以客户端从 `HEAD`、ZIP 的计划或 `Content-Range` 读取大小。
- **记录。** 每次下载、ZIP 和上传都是 `<data dir>/transfers.jsonl` 里的一行（权限 0600，超过 8 MiB 就轮换）：谁（Access 邮箱、`net:<地址>` 或 `local`）、什么、多大、上传的 SHA-256，以及怎么结束的；从不含查询字符串、令牌或文件内容。写不进的一行只在控制台说一次，绝不会让传输失败。README 的“远程访问：传输文件”写着规则、限制和代码；`tests/contract/folder-transfer.test.ts` 用真实的服务器按三种页面把它们跑一遍。

### 发布过程中发现并修好的问题

- **导入不会再因为一个不是普通文件的东西让服务器卡住。** 导入在替换一个文件之前，会先把它复制进备份；数据文件夹里如果有一个命名管道（放在像 `favorite-models.json` 这样的列表文件的位置），复制时会同步地打开它，于是整个服务器在有人往管道里写东西之前都不再回应。现在备份只复制普通文件和链接（管道、设备或套接字没有可保存的内容，恢复时会跳过它们），而一个不是普通文件的列表偏好会被当成错误，绝不会去打开它。
- **导入最后才说“完成”。** 以前它的状态在服务器重新读取被它替换的内容之前、在对话可以打开之前就变成了“完成”，所以一个马上去打开对话的页面可能会被告知导入还在写入。现在“完成”在这两件事之后才出现。
- **在手机上发送消息后，对话会继续跟着最新内容。** 发送进行中时，消息框下面那行字从两行变成一行，浏览器就把滚动位置往回裁掉这么多，页面把这次回裁当成了你向上翻阅，于是不再跟随回复。现在页面会在这个短暂的布局还在的时候就记下自己的位置。
