## English

### The built-in browser comes with the Mac app, and runs in Chrome's sandbox

The seven findings v0.21.0 left open for a decision are decided and fixed, together with one more found along the way. The tests that failed by chance in CI were tracked down one by one; six of them were real bugs, fixed below.

What you are most likely to notice:

- **The Mac app ships its browser.** CEF, the browser the agents of your conversations use in the app, is now inside the app (`Contents/Frameworks`) and is updated with it: there is nothing to install in Settings › Browser any more, which shows CEF's version and Clear browser data. The pages it opens run in Chrome's macOS sandbox, as in Chrome itself. The download is bigger for it (the dmg is about 189 MB instead of about 49 MB). The copies earlier versions downloaded into the data folder (about 330 MB each) are removed when the app starts.
- **A browser that is off costs nothing.** While Settings › Browser › Use the built-in browser is off when the app starts, the app does not load CEF at all (#188). Turning it on then restarts the app, as Clear browser data does.

### Every fix

- The Mac app's built-in browser ran its pages without Chrome's sandbox (#168)
- The browser's page list kept a page's first title (its address) when the page set its title later (#187)
- The @ completion offered a page that is not on this computer dotfiles and names that look like secrets, which its Files tab hides (#57)
- Restoring or importing over existing files could not work on Windows: the backups and the restore assumed POSIX paths (#77)
- The built-in browser's page could not be reached and left with the keyboard: it is now a tab stop, Enter or Space gives it the keyboard and Ctrl+F6 takes it back (#113)
- Try again after a failed omp install showed the old failure instead of running the install again (#122)
- A signing keychain that did not open was deleted and made anew, which lost the permissions macOS had given the app (#162)
- `omp-webui --stop` did not run the server's shutdown on Windows (#176)
- The Guidance tab put the conversation's text back over what was typed right after a save
- Opening New chat again before the conversation it had just started was shown reused that conversation's process instead of starting a new one
- New chat's project-name field could take the cursor from the message box while you were typing, so the text went into the folder name
- An app update that failed could stay stuck for good, refusing every later install, when a file it made could not be removed (Windows holds a program it just ran)
- On Windows a mode or setting change of a conversation could fail (EPERM) when omp was reading its settings file at that moment
- When omp ended, the reason the page was shown could be cut off on a loaded machine

### Tests and CI

- The tests that failed by chance in the last 100 CI runs were looked into one by one and fixed at their cause, among them the side-question cancel test (#43), the WebSocket tests on Windows (a Bun bug that loses a socket's data while a test waits through `expect(…).rejects`, oven-sh/bun#44429), process numbers Windows hands out again, and ports taken on one address only. Three could not be reproduced and remain watched: a palette change in the two-tab preferences test, the preset role tests on Windows, and one Windows update test, which now says where it got to when it times out.
- CI keeps Playwright's system packages in its cache, so the end-to-end jobs no longer hang for 40 minutes on a slow Ubuntu mirror; the export tests take omp's pinned viewer scripts from a cache instead of the network.

## 中文

### 内置浏览器随 Mac 应用一起提供，并运行在 Chrome 的沙盒里

v0.21.0 中留待决定的七个问题都已决定并修复，另外还修复了过程中发现的一个问题。CI 中偶发失败的测试都逐一查明了原因；其中六个是真正的缺陷，修复列在下面。

你最可能注意到的：

- **Mac 应用自带浏览器。** CEF 是对话中的智能体在应用里使用的浏览器，现在放在应用内部（`Contents/Frameworks`），随应用一起更新：设置 › 浏览器里不再需要安装任何东西，只显示 CEF 的版本和“清除浏览器数据”。它打开的页面运行在 Chrome 的 macOS 沙盒里，和 Chrome 本身一样。下载因此变大（dmg 约 189 MB，原来约 49 MB）。旧版本下载到数据文件夹里的副本（每份约 330 MB）会在应用启动时删除。
- **关闭的浏览器不占资源。** 如果应用启动时设置 › 浏览器 › “使用内置浏览器”是关闭的，应用完全不会加载 CEF（#188）。之后打开它会重启应用，和“清除浏览器数据”一样。

### 全部修复

- Mac 应用的内置浏览器在没有 Chrome 沙盒的情况下运行页面（#168）
- 页面之后再设置标题时，浏览器的页面列表仍显示它的第一个标题（它的地址）（#187）
- 不在这台电脑上的页面里，@ 补全会列出点开头的文件和看起来像机密的名称，而文件标签页会隐藏它们（#57）
- 在 Windows 上无法恢复，也无法导入覆盖已有文件：备份和恢复都假定是 POSIX 路径（#77）
- 无法用键盘进入和离开内置浏览器的页面：现在它是一个 Tab 停靠点，按 Enter 或空格让它接收键盘，按 Ctrl+F6 交回（#113）
- omp 安装失败后点“重试”显示的是旧的失败，而不是重新安装（#122）
- 打不开的签名钥匙串会被删除并重建，导致 macOS 给应用的权限丢失（#162）
- 在 Windows 上，`omp-webui --stop` 不会执行服务器的关闭流程（#176）
- “指引”标签页在保存后，会把对话原来的文字盖回到刚输入的内容上
- 在新对话刚启动的对话页面出现之前再次打开“新对话”，会沿用那个对话的进程，而不是启动新进程
- 输入消息时，“新对话”的项目名称输入框可能抢走光标，文字被输入到文件夹名称里
- 应用更新失败时，如果它生成的某个文件删不掉（Windows 会占用刚运行过的程序），更新会一直卡住，之后的每次安装都被拒绝
- 在 Windows 上，如果 omp 正好在读取对话的设置文件，更改对话的模式或设置可能失败（EPERM）
- omp 结束时，在负载高的机器上，页面显示的原因可能不完整

### 测试和 CI

- 最近 100 次 CI 运行中偶发失败的测试都逐一排查，并在原因处修复，包括取消旁问的测试（#43）、Windows 上的 WebSocket 测试（Bun 的一个缺陷：测试通过 `expect(…).rejects` 等待时会丢失套接字数据，oven-sh/bun#44429）、Windows 很快重复使用的进程号，以及只在一个地址上被占用的端口。有三个没能复现，仍在观察：双标签页偏好测试里的一次配色更改、Windows 上的预设角色测试，以及一个 Windows 更新测试（现在超时时会说明进行到哪一步）。
- CI 把 Playwright 需要的系统软件包放进缓存，端到端任务不再因为 Ubuntu 镜像太慢而卡住 40 分钟；导出测试从缓存而不是网络读取 omp 固定版本的查看器脚本。
